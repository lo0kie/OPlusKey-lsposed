### 自定义按键接线：从「只存在内存里」到「能收集、能绑定、能生效」

此前那版只做到「能在 ⋮ 菜单里收集几颗键、显示名字」，收集结果存在 `ui/state/KeyWatchState`
的一个 `mutableStateListOf` 里 —— 进程一死就没了，配置里没有它们，注入侧更不知道有这些键。
这次把它接完整：**收集 → 落盘 → 广播 → 认领 → 执行** 五段全通。

#### 身份：`KeyId` 从枚举改成类

- 枚举装不下「运行时才知道有几颗」的东西；而把运行时清单塞进伴生对象（一个可写注册表）
  会让 `core` 带上**跨进程可变状态** —— 三个进程各一份，谁先写谁说了算，正是本项目一直在躲的。
  现在是「清单只属于 `Config`（`custom_keys`），`KeyId` 只描述一颗键长什么样」。
- **判等按 `id` 手写**，不用 `data class`：后者会把 `label` 算进判等，于是「改个名」在
  `Map<KeyId, KeyConfig>` 里就成了另一颗键 —— 绑定全丢。
- `KeyId.PLUS` 仍是伴生常量，20 个 `KEYCODE_*` 常量与 36 处调用点一行没动。
- 自定义键 id 用 `ck1` `ck2`，**不用键码**：同一颗物理键换驱动就可能换码，绑定不该跟着丢。
- `fromId` / `fromKeyCode` / `fromAnyKeyCode` 保留但只认内置键（它们拿不到配置）；
  按 id / 码找键的入口在 `Config`：`keyIdOf` / `keyForId` / `keyForCode` / `keyForRawCode`。

#### 落盘：`custom_keys` 段

```json
"custom_keys": [ {"id":"ck1","name":"按键 1","code":1074} ]
```

空表不写这一段 ⇒ 没收集过按键的人，文件格式与从前逐字相同。新旧版本互相读都安全。
`CustomKeysCodec` 单独成文件（塞进 `ConfigCodec` 会先撞 detekt 的函数数上限）。

#### 广播：从「只发侧键」到「按颗发」

`ConfigBroadcast` 原来 `intent()` / `parse()` 都硬编码 `config.key(KeyId.PLUS)` ——
**自定义键的配置从来没进过 `system_server`**，这是「没接线」的真正根。

- 先放一份 `key_ids` 清单，再按 `<keyId>_<字段>` 逐键存：`plus_enabled` / `ck1_single` ……
- `ConfigFields` 里那四条 `*_EXTRA` 从 `plus_single` 改成基础名 `single`，前缀由
  `ConfigBroadcast.extraName()` 一处拼。
- 两处会**静默失效**的地方一并修了：
    - `ConfigChannel` 判主开关变化用的 `intent.hasExtra(ENABLED_EXTRA)` —— extra 改名后永远为假，
      「关掉接管」会失效；
    - 指纹 `tag()` 的类型分派 —— 不剥前缀，逐键字段全被当成「取不到值」，两份不同配置算出
      同一个指纹，界面就会谎报「已同步」。

#### 注入侧：认领按颗，闸门下移

- 删掉 `handle` 开头那句全局 `if (!ConfigChannel.takeOver) return false`。它是**侧键的主开关**，
  却挡在所有键前面：侧键关着时自定义键完全无效，侧键开着时自定义键又绕过自己的 `enabled`。
- 新增 `claimOrNull()`：认领与闸门只在这一处判（认得这个码 + 那颗键开着接管）。
  策略类路径认 `keyForCode`（含内部码 780/781/782），PM 兜底路径认 `keyForRawCode`（只认原始码，
  否则同一次按压会被判两遍）。
- `isSynthetic` 改成问配置。同时补上它成立的前提：**`KeyId.RESERVED_CODES`** ——
  动作会注入的码（主屏幕/返回/音量/媒体/截图/通知中心/最近任务/静音）加电源键，
  收集时一律拒绝。这样「认领的码 ∩ 可注入的码 = ∅」，不会自己注入、自己认领地自持循环。
- PLQ110 那种**真按键也带 `deviceId = -1`**：判据从「不是侧键的码就当合成」变成
  「配置认不出的码才是合成」，自定义键因此不会被误丢。
- 侧键仍走 `takeOver` 而不是直接读配置：那道闸里含「缺 `enabled` 的畸形广播不许改主开关」
  的判据，直接读配置会把缺项默认成 `false`，等于一条坏广播把模块关掉。

#### 宿主：手势到达时按配置解析键

`GestureReceiver.handle` 的 `KeyId.fromId()` 只认内置键，换成 `ConfigStore.read().keyIdOf()`。

#### 界面：清单即配置，绑定作用于当前键

- `KeyWatchState` 只剩「在编辑哪一颗」（存 id，不存对象 —— 改名会换实例，存对象对勾会落到
  已不存在的键上）。清单从 `Config.customKeys` 取。
- 收集 / 改名 / 删除分别走 `Config.withCustomKey` / `withKeyName` / `withoutKey` + `write`。
- `PageEntry` 的整页闸门从 `selected == null && plusKeyEnabled()` 改成
  **当前那颗键自己的 `enabled`**；`BindingActions.pick`、`ConfigWrite.setLongRepeat`、
  `ConfigReset.resetKeyBindings` 三处写死的 `KeyId.PLUS` 换成当前编辑的键。
- **收集即接管**：`withCustomKey` 直接给 `enabled = true`。自定义键没有独立总开关，
  页面闸门就是它自己的 `enabled` —— 默认关着的话用户刚收完键，绑定页整片灰、一个动作都选不了，
  而他没有别的地方能打开（死锁）。

### 已知缺口

- 自定义键**没有「暂时停用」的开关**（侧键有首页那个主开关）。要停用只能删掉那颗键。
- 收集时只认注入侧报上来的原始键码。若某颗键也被 ColorOS 策略类改写成内部码，
  它会认领不到（内部码是策略类给侧键专用的，见 `docs/device-findings.md`）。

### 新增一条文案

`key_watch.reserved`（「这颗键不能添加：模块自己会用到它」）—— 中英两本字典与 `Strings` 同步加，
三边仍是 311 / 311 / 311。收集时撞上 `KeyId.RESERVED_CODES` 就弹它，弹窗**不关**，
否则用户会以为是自己没按准。

### 配置与命令库改用 kotlinx.serialization（`org.json` 清零）

`ConfigCodec` / `CommandLibrary` / `ConfigBundle` / `I18n` / `Donor` 五处全部换掉平台自带的
`org.json`，仓库里 `import org.json` 现在**一处不剩**。

换的动机是两个把人坑过的行为，不是「换个库更时髦」：

- `optString(key, fallback)` 只在**键不存在**时走 fallback，遇到 `"single": null` 会返回字符串
  `"null"`（`JSONObject.NULL.toString()`）⇒ `Action.parse("null")` 兜底成 `Shell("null")`，
  按那个手势真去跑 `sh -c null`；
- `optBoolean(key)` 在键缺失时返回 `false`，与「明确写了 false」混在一起。

以前靠 `textOf` 这类手写清洗、以及 `ConfigFields` 那套元数据兜。现在绑到 `@Serializable`
的 DTO 上：缺字段走默认值，类型不对直接判「读不懂」，不会静默变成某个合法但错误的值。

- 新增 `ConfigDto`（含 `ConfigDto` / `KeyDto` / `GlobalDto` / `CustomKeyDto`）与
  `CommandLibraryDto`（含 `CommandDto`）。**线格式与领域模型分开**：`Config.keys` 是
  `Map<KeyId, KeyConfig>`，直接给 `Config` 加 `@Serializable` 得给 `KeyId` 写自定义
  `KSerializer`，还会让「加一个字段 = 改一次文件格式」。
- 命令库**不整份 `decodeFromString`**：它的纪律是「坏一条只丢一条」，所以先取 `commands`
  数组再逐条 `decodeFromJsonElement`，失败那条跳过（`parseOrNull` 则相反：任何一条认不出整份判坏）。
  `steps` 的元素类型写成 `List<String?>`，接住手改文件里常见的 `null`。
- `ConfigFields` 的 `*_JSON` 一列从此**只是文档**（没有代码读它），`*_EXTRA` 与 `Kind` 必须留着
  —— 配置广播的 extra 名与类型分派还靠它，kotlinx 管不到 Intent extras。类注释已改成如实描述。
- `Donor` / `I18n` 读的是**我们自己的 asset**，用树 API 就够，`:app` 因此只加运行库、不挂编译器插件。
- 自定义按键那次为 `custom_keys` 单独建的 `CustomKeysCodec` 随之删除 —— 那段现在是
  `ConfigDto.customKeys` 一个字段，不需要单独的段落编解码器。

### 配置格式升到 v2（老文件必须能读进来）

这一条是整批里**唯一有数据风险**的改动，单独说清楚。

原来 `digestMatches` 是把解析出的对象用 `org.json.toString(2)` **重新序列化**再比 md5 —— 也就是
「这份文件是否与 org.json 会输出的字节一致」。换序列化器后字节必然不同 ⇒ **每一份老配置的 md5
都会对不上** ⇒ 判读不懂 ⇒ `ConfigStore.read` 退回 `Config.DEFAULT` ⇒ 下一次写盘把用户的绑定与
开关整份抹掉。`ConfigCodec` 的注释里记着真机发生过一次同类事故（「振动开关自己变 false」）。

所以按版本分档：

- **`version <= 1`（老文件）**：不校验 md5，只要求「能解析 + 键段完整」——`keys` 里必须有全部
  内置键、每个 `custom_keys` 条目也得在 `keys` 里有对应段。老文件因此能无损读进来。
- **`version >= 2`**：md5 = 「把 md5 置空后重新编码」那份文本的 MD5，对不上判读不懂。
- 写盘一律写 v2。**不需要单独的迁移步骤**：老文件读进来后第一次写盘自然升级。

**降级风险（已知，未处理）**：装回旧 APK 时，旧代码按 org.json 口径重算 md5、对不上、判读不懂，
随后退回默认值并写回 —— 配置会丢。回滚前得先备份 `opluskey_config.conf`。

### 原子写换成 `android.util.AtomicFile`

`ConfigStore.writeAtomically` 原来是自己拼带 pid + 时间戳的 `.tmp`、`fd.sync()`、`renameTo`。
那套能挡住「读到半截」，但**挡不住写完之前断电 / 进程被杀**：目标已经没了、`.tmp` 还在。

现在走 `startWrite` → 写字节 → `finishWrite`（flush + `fsync` + 旧文件 → `.bak` + `.new` → 目标），
失败 `failWrite` 自己收半截。两处补丁：

- **`openReadable` 的 chmod 要自己补**：`AtomicFile` 只认「写 + 还原」，不知道我们要把文件放开给
  别的 uid 读。落在 `finishWrite` 之后、对**目标文件**做（原来是对 tmp 做、靠 rename 带过去）。
- **并发防御退化**：原来 tmp 名带 pid + 时间戳，两个写方各写各的、字节不互相掺；`AtomicFile`
  固定用 `.new`。当前写方串行（页面写配置、命令库写命令），跨进程同时写本来也没有锁保护，
  所以接受这个退化，KDoc 里写明了。

### 应用图标改成直接绘制（不再走中间位图）

`AppTile` 原来是每个图标 `createBitmap → Canvas → drawable.draw → asImageBitmap`：每滑过一个应用
就在 Java / Native 堆各分配一张 48dp 位图，还多一次整块拷贝。

新增 `ui/DrawablePainter.kt`（内联约 90 行，**没引 accompanist** —— 那个库已进入维护模式，
而我们只要一个 `Painter`）。三个实现细节都是对着本项目的实际情况定的：

- **不实现 `applyAlpha` / `applyColorFilter`**（返回 `false`）：Drawable 来自 `AppPickerState` 的
  缓存、可能被多行共用，改它的 `alpha` 会把状态留在对象上，别的行下次画出来跟着变。
- **`onDraw` 里会改 bounds**：那是 `Drawable` 唯一的绘制接口，绕不开；绘制都在主线程串行、
  每次画前重设，所以共用也不会串。
- **`applyLayoutDirection` 也返回 false**：应用图标本来就不随方向翻转。

顺带删掉只为位图路径存在的 `APP_ICON_BITMAP_SIZE`（48dp）——留着就是失效常量。

### shell 执行线程入池

`ShellRunner` 的两条 `Thread {}`（等子进程 / 读输出）是**每条命令硬建**的，连发时就是反复创建
销毁 Java 线程。改成两个有界线程池：

- **执行池与读线程池分开**，各自 `SHELL_MAX_CONCURRENT` 个。**不能共用一个**：执行那条会 `get()`
  等读线程结束，共用池在「三条执行线程都在等、读任务还排在队列里」时就是死锁。
- `allowCoreThreadTimeOut(true)` + 60s 回收：按键是低频动作，池不该常驻。
- 用 `LinkedBlockingQueue` 而不是 `SynchronousQueue`：后者池满时抛 `RejectedExecutionException`，
  而**读线程被拒等于这次命令的输出没人读**。排队的那条由 `SHELL_DRAIN_JOIN_MS` 兜住。
- `startOutputReader` 的返回类型 `Thread` → `Future<*>`；`reader.join(ms)` → `reader.get(ms, …)`，
  **保持 `runCatching` 包着** —— `join` 超时静默返回，`get` 会抛 `TimeoutException`。

**没有换掉 `ProcessBuilder`**：每次按键仍有 ~100ms 的 fork + execve。这是有意的取舍 —— 这套东西
跑在 `com.android.settings` / `com.oplus.uiengine` 里，ColorOS 的冻结策略会把常驻的 root IPC
管道冻成坏连接，而「用完即焚」的进程没有状态可以坏。libsu 那种守护进程模型因此不采用。

### 性能参数集中到 `host/action/ShellLimits.kt`

`SHELL_MAX_CONCURRENT` 与 `SHELL_THREAD_IDLE_SECONDS` 从 `ShellRunner` 里拎出来。

**没有放进 `ui/model/PageMetrics.kt`**（那是同类东西的集中处）：`PageMetrics` 在 `ui/`，
而 `host/` 不许依赖 `ui/`（`docs/decoupling.md` 动作 1、2，`audit-coupling.py` 会报错）。
同包里已有先例 —— `MiniWindowFacts.kt` 也是把一族的常量从执行类里拿出来单独放。

两条常量的 KDoc 一起搬过去并补了约束：并发上限说的是「两个宿主进程加起来最多几条」
（槽位由 `FileLock` 跨进程守），线程池上限跟着它走、两个数必须一起改。

- `i18n` 模板与参数对不上时留一行；负命中按 loader 分开记；图标缓存键带 userId；捐赠金额夹掉负数
- `shortcut:` / `intent:` 补上字形（不再落 `Dots`）；首页标题兜底走字典
- 工具链：`audit-coupling` 根包文件并入 root 档、`ui.component` 那条空转的禁止边撤掉（边数 31 → 30）；
  `check_variants` 去掉空转循环；proguard / CI / `verify-apk.sh` 里几处过期路径与重复的判据编号

### Shell 并发：本地降级那一路被当成「已满」

- 锁文件建不出来时退回本进程计数，占到的哨位是 `-2`，而外层用 `slot < 0` 判「已满」——
  于是那台机器上所有 `shell:` 命令全被拒，且那一次计数已加、走不到释放（三次之后彻底不再放行）
- 判据改成只看 `NO_SLOT`（`-1`）；哨位 `LOCAL_SLOT` 仍是 `-2`，两条路互不相干

### 跨进程锁：别再去开本进程已占住的槽

- 遍历槽位时先跳过 `heldSlots` 里已有的格子。Linux 的 fcntl 锁按「进程 + inode」记，
  同一个进程关掉指向该文件的**任意** fd 会放掉这一 inode 上的**全部**锁 ——
  再开一次、`tryLock` 抛 `OverlappingFileLockException`、`close()` 那一下就把别的线程正持有的锁抹了

### 宿主进程漏注册「导出日志」广播

- `onReceive` 里写了 `ACTION_LOG_PULL` 分支，注册接收器时却漏加这条 action ⇒
  导出的日志里永远缺宿主主进程那一段。补进同一个 `IntentFilter`

### 屏幕旋转冻结的参数顺序

- `freezeDisplayRotation(displayId, rotation, caller)` 传成了 `(rotation, 0, caller)`：
  横屏下等于去冻一个不存在的 displayId，抛异常 ⇒ 横屏时自动旋转锁不住（竖屏恰好蒙对）

### WLAN 开关：被系统拒也报成功

- `setWifiEnabled` 被拒时返回 `false`，代码却以「调用没抛」为成功 ⇒ 上游当成切好了。
  改成看返回值

### 状态栏本地调用补 Binder 身份

- 通知中心 / 控制中心 / 电源菜单 / 最近任务这几处反射调用统一包一层
  `clearCallingIdentity`（`finally` 还原）：整条链路从宿主进程的 Binder 事务进来时，
  目标服务按调用方判权限会抛 `SecurityException`

### 界面按「当前编辑的那颗键」取值

- `actionOf` 写死 `KeyId.PLUS`：切到自定义键之后，网格高亮、打勾项、小标题、长按串行判定
  全按侧键的配置算（改了看不出来）。改成 `KeyWatchState.editing(cfg)`
- 「长按连续触发 / 触发间隔 / 长按延迟」四处读写同样写死侧键：停在自定义键上拨开关、拖滑杆
  改的全是侧键。读与写都跟着当前编辑的键走

### 收集按键：查重比「全部键」

- 原来只比 `customKeys`：按下侧键会被收成一颗影子键，而分发时先匹配到侧键，这颗永远触发不了。
  改成比 `allKeys` 的认领码

### 配置增删的两处口径

- `withoutKey` 补上「内置键不可删」：误删 `plus` 等于把侧键整条从配置里抹掉，读回来退回默认值
- `withCustomKey` 先摘同 id 的旧条目再追加：`customKeys + key` 会留两条同 id 的，删一颗只删掉一条

### 广播：每颗键各自算 `longIsSerial`

- 原来只算侧键那一份，自定义键恒为 `false` ⇒ 注入侧把它的串行命令当单条动作，连发闸门失效。
  `ConfigBroadcast.intent` 改成逐键回调（`CommandLibrary.longIsSerial(config, key)`）

### 删掉一颗键也要撤掉已排下的手势

- `newlyOff` 遍历的是**新**配置的键清单：被删掉的那颗已经不在里面，判定永远为假 ⇒
  删键那一刻按住不放会一路派发到连发上限。改成遍历旧配置

### 注入侧导出日志补一层 try

- `ACTION_LOG_PULL` 那支在 system_server 主线程上裸调 `SystemContext.get` / `LogWire.reply`：
  任何异常都会把整机拖去重启。与旁边几支同一纪律

### 手势判定：直判时刻按颗存

- `lastDirectSingleAt` 原来是全局一个：A 键刚直判过单击，B 键紧接着那一下会被算成「已派发过」
  而吞掉（快速在两颗键之间敲、短按 A 再长按 B 都会中）。挪进每颗键的待定状态

### 连发超时补一次「松手」

- 超过 30s 没等到抬手时原来只 `reset`：连发停了，但带「松手结束」语义的动作（灵感语音录音）
  收不到松手通知，录音还在继续。改成 `finish`

### 读盘走 `AtomicFile`：只剩 `.bak` 时先还原

- 写盘是「base → `.bak`、`.new` → base」两步，中间被杀 / 断电会留下「base 不在、`.bak` 在」；
  而读的时候直接 `f.readText()`、且先判 `isFile` ⇒ 判成「首装没配过」，用户整份配置随后被默认值覆盖
- `ConfigStore.readText` 改走 `AtomicFile.openRead()`（它会用 `.bak` 还原）；配置与命令库两处
  的「文件在不在」改由 `FileNotFoundException` 判

### 解码容忍显式 `null`

- `Json` 打开 `coerceInputValues`：手改 / 外部工具写出一个 `"keys": null` 时回退 DTO 默认值，
  不再让整份配置被判「读不懂」（页面随即只读，怎么改都存不进去）

### 改名命令时所有键的绑定一起挪

- 原来只挪侧键那份 `cmd:旧名`：自定义键上绑的同一条命令改名后按下去是 NOT_FOUND，
  而界面报的是「已修改」。改成遍历 `allKeys`

### 按键菜单的弹窗取实时配置

- 改名 / 删键的确认回调捕获的是组合期那份配置快照：弹窗开着时别处写过配置，回写会把那次改动抹掉；
  删键还不管写没写成先 `forget` 选中态（写失败时界面与配置脱节）

### Shell 并发槽位：进程内也要互斥

- `acquireSlot` 里「检查 `heldSlots` → 开文件 → `tryLock` → 写 `heldSlots`」这一段原来是可交错的：
  两条线程同时申请同一格时，后到的那条 `tryLock` 失败、`close()` 自己的 fd —— 而 POSIX 规定
  关闭指向某 inode 的**任意** fd 会放掉本进程在该 inode 上的**全部**锁，先到那条的锁就这么没了
- 申请与释放都进同一把进程内锁（叶子锁，只包本地状态与文件操作）；`heldSlots` 的读写一并被护住

### 满槽位不再误退「本进程计数」

- 上一版用「`opened == 0` 就退回本进程计数」判「锁文件开不出来」，而本进程已经占满三格时
  循环全被 `continue` 跳过、`opened` 同样是 0 —— 于是能再跑三条本地 shell，上限从 3 变 6
- 判据补上「且 `heldSlots` 为空」：只有一格都没占、一个文件都没打开，才算锁机制坏了

### 合成事件判据改成「这个码是不是我们会注入的」

- 原来问的是「配置认不认识这个码」（`keyForCode == null`）：收集弹窗里按下一颗**还没收集**的
  物理键时配置里当然没有它，而这块 ROM 的真按键（PLQ110 实测）也带 `deviceId = -1` ⇒
  被当成我们注入的合成事件放行，新键永远收不进来
- 改成「码在 `KeyId.RESERVED_CODES` 里（动作能注入的那批，且一律不许被收集）+ 虚拟设备号」

### 反射负命中清理删错了键

- `findClass` 的负命中表键是「loader 身份 + 类名」，删的时候传的却是裸类名 ⇒ 那条记录永远删不掉，
  静态表只涨不落，下次同名查找还会被一条早已过期的负命中挡住

### 动态代理的零值不再被吞成 null

- 小窗动画那个回调代理用 `runCatching { zeroOf(...) }.getOrNull()` 包了一层：一旦返回 null，
  框架对 `boolean` / `int` 返回值拆箱就是 NPE，而它跑在 system_server 里。改为直接返回零值

### 启动成功码只认 0..3

- `startActivityAsUser` 返回的是 `START_*`：后台启动被拦时是 `START_ABORTED`（102）/
  `START_RETURN_LOCK_TASK_MODE_VIOLATION`（101），而判定写的是 `code >= 0` ⇒ 系统拒绝被报成
  「已下发启动」，失败提示与回退整条都不触发

### 按键上报挪出 InputReader 线程

- `KeyWatch.report` 原来在 InputReader 线程上同步 `sendBroadcast`：AMS 一次瞬时锁竞争就会卡住
  全局按键读取（丢帧 / Input ANR）。改成主线程 `handler.post`

### 抬手与长按到点互斥

- 输入线程的 `onKeyUp` 与主线程的长按枪可能在同一毫秒都通过各自的判定 ⇒ 一次按压既执行长按、
  又执行单击。两边的「读状态 → 派发」改成在同一把每键锁里做，派发留在锁外

### 配置读写两处收口

- `readText` 里 `readBytes().toString(Charsets.UTF_8)` 换成 `decodeToString()`（前者已废弃）
- `writeAtomically` 补进程内互斥：`AtomicFile` 固定用同一个 `.new` 临时文件，两条线程同时写会掺字节

### 两处文案与空安全

- 命令免责声明里「不会**对的**命令做任何检验」补成「不会对**编写的**命令做任何检验」
- `HostChrome` 刷窗口底色时 `activity.window` / `decorView` 改成安全调用（销毁后取到 null 时
  不再靠外层 catch 兜）

### 手电筒：ColorOS 那条没连上时重读一次真值

- 回退闭包里捕获的是「受理前读的那一次」，而受理那条路直接 return、那次读**根本没发生** ——
  闭包里的 `false` 不是真值，回退到 CameraManager 时会把开着的再开一次
- 回退那一刻重新 `syncStateFromSettings`；原来那个可变的 `colorOsStateKnown` 一并去掉

### 分身：用户表备忘录的并发安全

- `unresolvedUsers` 从 `HashSet` 换成 `ConcurrentHashMap.newKeySet()`：后台协程 `entries()` 会
  `clear()`，界面线程 `slotOf()` 同时读改写 —— 并发改 `HashSet` 有 `ConcurrentModificationException`
- 同一处的 `cachedUsers` 补 `@Volatile`：写它的在后台、读它的在界面线程

### 分身查询：flags 的类型跟着 AIDL 走

- `IPackageManager#queryIntentActivities` 的 flags **Android 13 起是 `long`**（AOSP AIDL 确认），
  而这里只按 `int` 找 ⇒ 新 ROM 上恒为 null，分身那一槽整块消失、日志只说「没有这个方法」
- 先按 `long` 找、找不到再退回 `int`；实参也跟着签名给（`0L` / `0`），传错会 `IllegalArgumentException`

### 流体云客户端：绑定超时与 Context

- 绑上了 ≠ 连上了：`onServiceConnected` 不来时 `isConnecting` 永远是 true ⇒ 之后的消息只进队列、
  再也不发起重绑。补 3 秒复位闸（仍未连上就把 `isConnecting` 放开，下一条消息重新绑）
- 绑定改用 `applicationContext ?: context`：传进来的可能是 Activity，绑住的连接会把那个 Activity 钉住

### ROM 告警位补 `@Volatile`

- `effectiveWarned` 与旁边的 `landingWarned` 是同一笔「只打一次」，但少了注解 ⇒ 多线程首次进来时
  可能各打一行

### 小布快捷指令的广播去掉 activity flag

- `sendBroadcast` 的 Intent 上挂 `FLAG_ACTIVITY_NEW_TASK` 没有意义，只会让读日志的人以为这里在起界面

### 音量±与电源允许被收集

- 这两颗原来在「不许收集」那张表里（理由：电源 / 音量必须交给系统）。用户口径改成**允许自定义**
- 码表拆成两张：`INJECTABLE_CODES`（动作会注入的那批，判「合成事件」用）与
  `RESERVED_CODES`（不许收集）= 前者减去音量±与电源。两张表**不能合并** —— 音量 / 电源
  注入的那一下仍要认出来放行，否则收下它们就成自持循环
- 收集期一律吞：弹窗是模态的，按什么都是在报键；剩下那几颗收不下的（主屏幕 / 返回 / 媒体 /
  截图…）会 toast 一句原因。代价是收下并启用之后，那两颗键归模块管（没收集时照常放行）

### 收集期吞下的「按下」，抬手也要吞

- 只吞 DOWN 的话，弹窗往往**因为这一下而关掉**（收下了 / 被手动关掉），紧跟的 UP 落在收集期之外 ——
  判定器收到一条没有按下的 UP，按「孤立抬手」补判一次单击，侧键的动作照样执行
  （真机实测：弹窗一关，侧键立刻跑了一次 OCR）
- 记下「这颗码的按下刚被吞过」（5 秒内有效），它的抬手一并吞掉

### 侧键不进「可自定义」清单

- 按下侧键原来会被当成「已添加过」：选中侧键那一组、弹窗直接关。现在按「不是候选」处理 ——
  toast 一句「这颗键不能添加」，弹窗继续等下一颗
- 判据与保留码同一处出口（`collectKey`），`ReturnCount` 仍是 4

### 自定义按键上限三颗

- `KeyId.MAX_CUSTOM_KEYS = 3`，收集入口按它拦，到上限 toast「最多只能添加 %d 颗按键」

### 菜单里的字形：收集到的键按序编号

- 收集到的键按**它在清单里的位置**取数字：`number-1` / `-2` / `-3`（上限三颗，所以 `else` 兜到 3）；
  「添加按键」用 `plus` —— 两行不再共用 `pointer-plus`；重命名弹窗的行首也跟着
  换成「正在改的那颗」的编号
- 收满三颗时「添加按键」**置灰**：点了也只会 toast 一句「到上限」，不如直接说不能再加
  （禁用行会吃掉点击、菜单不关）

### 「重置绑定」改名「重置此按键绑定」

- 菜单行与确认弹窗标题同一句；英文 `Reset this key's bindings`
- 菜单行标题的截断上限跟着放到 14 格（七个汉字）—— 这一句本身就有七个字

### 连发间隔下限 100ms → 50ms

- `KeyConfig.MIN_REPEAT_INTERVAL_MS` 放到 50：滑杆下限跟着走（默认仍是 300ms）

### 无底部按钮的弹窗：正文底部与标题顶部对称

- 库把 `content` 槽**留空**（好让按钮条横跨整个面板），标题上边距却是 `insideMargin.height` ——
  没有按钮条时正文直接贴到面板底边，比标题那一档紧一大截
- 收集弹窗的等待态（没有底部按钮）补 `dialogBottomMargin()`，取同一档；有按钮的结果态不动

### 每颗键一份判定参数（不再共用全局）

- 「单击延迟」与「忽视无操作双击手势」从 `GlobalConfig` 搬进 `KeyConfig`：每颗键各有一份，
  改一颗不会带动另一颗（用户口径：每颗键的数据互不依赖）
- 字段表里这两项从 `GLOBAL_FIELDS` 换到 `KEY_FIELDS` ⇒ 广播变成逐键的
  `<keyId>_double_click_ms` / `<keyId>_instant_single`，注入侧按「这一次是哪颗键」取
- 判定侧：`SideKeyInterceptor` 不再在入口处刷全局值，改成 `feedDetector` 里按这颗键的那份刷
- 老文件里这两项还在 `global` 段：`ConfigDto` 读的时候拿它给每颗键兜底（迁移），
  下一次写盘就变成逐键字段

### 配置格式版本抬到 3（修「配置读取失败」）

- 症状：装上新包之后设置页顶着「配置读取失败，请重进页面」，改什么都存不进去
- 原因：`md5` 的口径是「按**当前** `ConfigDto` 重新编码」，而这一轮把 `doubleClickMs` /
  `instantSingle` 从 `global` 搬进了 `KeyDto`；`encodeDefaults = true` 会把新字段写进重编码结果
  ⇒ 老文件（v2）自己那份 `md5` 与它重编码后的字节必然不同，**每一份老配置当场全被判成读不懂**
- 现场核对（离线解码真机那份 `opluskey_config.conf`）：`version: 2`，`keys.*` 里确实没有
  `doubleClickMs`，`md5` 与它自己那份形态自洽（`e4e23a6f…`）—— 文件没坏，是读的一侧口径变了
- 修法：`ConfigCodec.VERSION` 抬到 3，判据从「`version >= 2` 才校验」改成
  「**`version == VERSION` 才校验**，更老的一律只要求结构成立」—— 老文件读进来之后下一次
  写盘自然升级成 v3 并带上新 md5，用户的绑定与开关一个不丢
- `md5` 对不上那条日志补上版本号：以后再撞上，一眼能分辨「版本号没抬」与「正文真被改过」

### 收集到键之后另开一个弹窗

- 收集（等按键 / 等确认）与结果（收下了 / 本来就有）拆成**两个 `OverlayDialog`**：出结果时
  收集那个关掉、结果那个另开（用户口径：不要用同一个浮层换正文）
- 于是两边的标题与按钮各归各的语义：收集那个没有底部按钮（等着按键，没有第二步可点），
  结果那个有「确定」；「已经在清单里」那一档仍然不摆按钮，底部内缩取标题上边距那一档
- `CollectState` 那三个态收成两个变量（`confirmCode: Int?` + `result: CollectResult?`），
  `Confirm` 里那个 `label` 计算属性改成 `CollectConfirmBody(code)` 里现算
- `dialogSideMargin()` / `dialogBottomMargin()` 挪进 `ui/ConfirmDialog.kt`（弹窗公共件）：
  `CollectKeyDialog.kt` 的函数数本来撞在 detekt 的 11 上限上

### 重命名之后首页报「设置未同步」（引用 vs 结构相等）

- 症状：给自定义按键改名，文件里已经是新名字，页面却顶着「设置未同步，重进本页即可」，
  而且恰好是**写下去 2 秒后**才冒出来（那是 `CONFIG_IN_FLIGHT_GRACE_MS` 的宽限到期）
- 根因：`ConfigState.config` 是默认的 `structuralEqualityPolicy`，而 `Config` 的结构相等
  **看不见按键名** —— `KeyId.equals` 只比 `id`（有意的：改名是改显示、不是换一颗键）。
  于是「只改了名字」的那份新配置与旧配置 `==`，`config.value = next` 被 Compose
  **整条丢弃**、连实例都不换：页面继续拿着旧实例，本地指纹（`ui/LinkCheck` 的

  （真机日志：它回 `83b1810c`，与离线按文件复算的值一致），两边对不上 ⇒ 判「未同步」
- 更糟的一层：下一次写盘会把旧名字写回文件，用户刚改的名字被抹掉
- 修法：`ConfigState.config` 换成 `referentialEqualityPolicy()` —— 配置是不可变快照、
  每次写盘都换新实例，**换实例本来就该重画**，这才是它该有的语义
- 离线复核（`.temp/tag_calc.py` 按 `ConfigBroadcast.intent` + `tag` 的口径复算）：从真机那份
  `opluskey_config.conf` 算出来的指纹与注入侧回的 `83b1810c` 逐字一致，确认问题在读的一侧

### 一次退多级只播一段转场

- 现象：一次 pop 掉两层时，**两个页面一前一后地滑出去**（中间那一层也跟着位移）
- 根因在库的模型里：coui-nav 用「一个 `animatedTop` 浮点 + 一张 presented 列表」驱动转场 ——
  一次组合里少 N 个 entry，那 N 层会**一起**位移，看着就像两页同时退场
- 改成两步（`SettingsPage.navTo`）：
  1. **这一帧**先摘掉中间那几层。它们被栈顶整幅盖着（`opaqueDepth = 1f`），摘掉不动栈顶
     ⇒ `animatedTop` 不变 ⇒ 没有可见位移；
  2. **下一帧**（`Choreographer.postFrameCallback`）再摘栈顶 —— 库才推那一段
     「栈顶滑出去、目标页滑进来」。
  第二步必须落在下一帧：同一帧里删完等于还是一次少 N 个，又回到两页一起滑
- 退一级不受影响（还是原来的单次 `removeAt`）；**返回该退几层还是几层**，没有加任何限制
- 第二步带一道身份校验（`lastOrNull() == top`）：这一帧里栈又被改过就不补这一步

### 提示条（Snackbar）三处观感问题

真机取样（PLK110，1272×2772）逐像素核过：

- **打开时向右轻微平移又拉回** —— 库给每条提示套了一层横向 `AnchoredDraggable`（横滑收走），
  锚点是第一帧之后才量的：出现那一下 offset 还停在锚点之外，胶囊先右移、锚点量好再被弹簧拉回。
  传 `canSwipeToDismiss = false` 关掉它 —— 我们的提示要么是常驻结论（代码收）、要么几秒就走的
  回执，本来也不需要手势收。修完同一条取样：胶囊中心 x = 636 = 屏宽一半，逐帧不动
- **底边影子在打开过程中被切一刀** —— 同一层 draggable 把条目挪出了视窗，影子落在裁切边界外。
  关掉之后胶囊下沿往下 76px 的光度是 229 → 241 的连续衰减（每 4px 变化 ≤1），没有硬边
- **连续两句时第二句从更高的地方瞬回** —— 库的 host 不是「一收就没」：条目留着画完退场动画、
  动画结束才从队列摘掉。原来是「收掉上一句 + 立刻弹下一句」⇒ 两句同时在队列里，
  后一句先排在上一句**上面**，等上一句摘掉再落回底边。
  `HostLinkState.hint` 改成先 `dismiss`、再 `join` 上一条的协程（`showSnackbar` 挂到条目真摘掉
  才返回），这才弹新的。修完 mid/end 两张取样里胶囊 bbox 完全一致（x[504,768] y[2445,2626]）

### 提示条换成自己画的那一颗（库的 host 整个不用了）

上面那三条都是**绕**着库的 `SnackbarHost` 修的，但它那两个结构性问题（`LazyColumn` + 每项一层
`AnchoredDraggable`）在外面关不掉。最后整条换掉：

- 状态侧：`ui/state/HintState.kt` 一行一个 `HintState`（同一时刻只有一句话，换内容就是换字符串），
  `HostLinkState` 里两行 —— 常驻结论（不自动收）+ 操作回执（2.2s）
- 渲染侧：`PageSnackbar.kt` 自己排两行 + 自己画胶囊。没有队列就没有叠放，没有 drag 容器就没有横向漂移
- 胶囊外观仍取库的公开常量（`SnackbarDefaults` 的圆角 / 内边距 / 字号 / 配色），
  **但不用库的 `Snackbar`**：它把外边距写死在自己身上（`padding(16dp, 4dp)`）且只收 `modifier`，
  磨砂画出来会带一圈 16dp 的糊边（`CommandToolbar` 当初踩的是同一个坑）

#### 落点改成与 COUI 一致

- 距屏幕底边 **32dp** = 库 `SnackbarHost` 的 `contentPadding`（28dp）+ 胶囊自己那 4dp
  （`coui_snack_bar_margin_bottom`）。之前 12dp 太贴底（用户反馈），再之前 52dp 又像悬在半空
- 页面是边到边（`contentWindowInsets` 全零），Scaffold 把提示槽贴在窗口底边 ⇒ 这个数就是到屏幕底边

#### 换句时宽度动画

- `animateContentSize(alignment = Center)` 挂在**底色之后**：它动的是这一颗节点报给外层的尺寸，
  前面那几层（阴影 / 糊 / 底色）都按这个尺寸画 ⇒ **一颗**胶囊从中间往两边长，不是两颗交叉淡化
- 文字换得干脆，长出来的那几帧被 `clip(胶囊)` 裁在边上 —— 观感是「长出来」

#### 三处必须记住的坑（真机逐条验过）

1. **`AnimatedContent` + `SizeTransform(clip = true)` 会把阴影四周裁平** ——
   那个 `clip` 裁到容器框，而容器框贴的就是胶囊边。第一版就是这么写的，被用户当场看出来
2. **`AnimatedContent` / `Crossfade` 的 alpha 会让磨砂消失** ——
   交叉淡化给整棵子树套 alpha，磨砂层也在里面 ⇒ 换句那一百多毫秒里糊没了、半透明底色直接透出
   底下的内容（用户口径「模糊会不见透出底部区域」）。这也是换句改走 `animateContentSize` 的原因
3. **进出场也不能用淡入淡出** —— Compose 给 alpha < 1 的节点开会话层（`saveLayer`），
   会话层的边界就是节点边界 ⇒ 画在胶囊外面那圈阴影**四周被裁**（用户口径「打开过程中四周阴影
   还是被裁切」）。改成只用缩放（COUI 那两个 `animateSpring`：show 0.3 / hide 0.25 响应），
   缩放是纯变换、不开层，阴影全程完整

  同一颗）：三处填的都是「一个名字」；「第几颗」在标题与副标题里已经说过了
- `FrostedDialog` 顺带接管了两件通用行为：弹窗打开前收软键盘（带输入框的弹窗是先弹窗再叫键盘，
  两者不冲突）、页面离开时跟着关（`OverlayCloser`）

### 自定义电源键「双击绑定系统按键」没反应（真机日志定位）

- 现象：把**电源键**收成自定义键（`ck4`，code 26），双击绑成「系统按键 → 音量 +」，
  双击没有任何反应
- 日志证据（真机，一秒内的三段）：

  ```
  .645 mIsPowerKeyDown =true                     ← 第二下按下（电源键按着）
  .659 按键 4·双击 → keyevent:24 / 合成事件 keyCode=24 放行给系统
  .659 PhoneWindowManager: handleKeyGestureEvent:gestureType=56 …   ← ROM 当成组合键，吞掉
  .725 mIsPowerKeyDown =false                    ← 电源键这时才抬起
  ```

  同一套注入换个时机是好的：`adb shell input keyevent 24` 能让音量从 28 走到 38，
  事件参数（`source=0x101 / deviceId=-1 / displayId=-1 / flags=0`）与我们的注入逐字相同
- 根因：双击是在**第二下按下**那一刻派发的 —— 那时触发键自己还按着，ROM 把随之注入的音量键
  判成「电源 + 音量」那一手（`mIsPowerKeyDown` 为真时的组合键窗口）整条吞掉
- 改法：**双击改成在第二下抬手派发**（`GestureDetector`）。`onKeyDown` 认出双击后只置
  `doubleFired`，派发挪到 `onKeyUp` 的 `doubleFired` 那一支。代价是晚几十毫秒，手感看不出来；
  好处是注入时触发键已经抬起，不再落进组合键窗口
- 同一处还写着：`reset` 会清 `doubleFired`，所以抬手那一支要先置假再 `reset` 再派发
- **注入侧在 system_server 里，改完要重启手机才生效**（LSPosed 是开机注入的）

### 消息条出场：缩一下就停住再凭空消失

- 原因是**临界弹簧的尾巴**：`dampingRatio = 1` 的弹簧到后段是渐近的，最后几个百分点走得
  像停住了，而节点是在动画**结束**那一刻被摘掉的 ⇒ 看到的是「缩一下 → 停住 → 没了」
- 出场改成 `tween(160ms)` 匀速走完，缩到 **0.72**（比进场的 0.8 更小）：没有淡出可借，
  只能让「消失」发生在明显还在缩的那一刻，而不是停稳之后再摘
- 进场仍用 COUI 那条 show 弹簧（终点就是静止态，尾巴慢下来正好收住）

### 弹窗输入框：光标落在末尾；带输入框的弹窗不再自己收键盘

- **光标在开头**：库的 `InputField` 只收 `String`，而 Compose 的 `BasicTextField(String)` 新建
  内部状态用的是 `TextFieldValue(text)` —— 那个构造器的默认选区是 **0**。于是预填了名字
  （`按键 N` / 当前名）的弹窗一聚焦，光标贴在开头，接着打字就插到最前面
- 拿不到 `TextFieldValue` 就改不了选区，所以走键盘那条路：Compose 的 `defaultKeyMapping`
  认 `KEYCODE_MOVE_END`（映射到「光标到末尾」那条命令，`KeyMappingKt` 里能查到），
  聚焦后往**当前窗口**发一次即可。`IconInputView` 加了一档 `caretToEndOnFirstFocus`，
  只在**第一次**拿到焦点时发（用户点出去再点回来不该把光标甩到末尾）
- 窗口必须是**弹窗自己那棵视图树**：`LocalView` 在 `Dialog` 内容里拿到的才是弹窗那个
  `ComposeView`，在页面那一层拿会发到页面的焦点上，弹窗里的输入框收不到
- **聚焦后又自动失焦**：上一轮把 `hideIme` 挪进了 `FrostedDialog`，那个 effect 在 `show`
  变 true 那一帧跑；当键盘正露着（上一个弹窗刚叫出来）时它会把键盘收掉 —— 而 `FocusOnShow`
  刚把焦点交给输入框，看起来就是「聚焦了一下又没了」。加了一档 `hideImeOnShow`
  （默认 `true`，给没有输入的确认窗用），「重命名 / 添加按键」传 `false`

### 消息条出场：改成缩到「没有」

- 上一版缩到 0.72 就摘掉，真机反馈「缩一下、停在那儿、瞬间没」—— 因为**摘掉的是一个完整的胶囊**
- 现在缩到 `0f`（tween 180ms，缓动换成 `FastOutLinearIn`：越接近消失走得越快，
  收在「还在动」的那一帧上）。被摘掉的那一帧本来就没东西，消失被这段收缩吸收掉了
- 60fps 逐帧核过（PLK110，636×1386 半分辨率录制）：172→190 帧是一路缩小的连续变化，
  191 帧起画面回到无提示 —— 中间没有「停住」的平台段

### 电源键当动作：注入那条路走不通，改走 PowerManager（真机验证）

- 现象：双击绑定成「系统按键 → 电源键」，双击没反应；换成音量 ± 就有反应
- 真机日志把两件事拆开了：**手势与执行都跑到了**
  （`按键 4·双击 → keyevent:26（宿主进程执行）` 后面紧跟 `合成事件 keyCode=26 放行给系统`），
  但 `dumpsys power` 里 `mWakefulness` 一点没变 —— **系统不接受注入的电源键**
- 同一个注入换音量键就好使；`adb shell input keyevent 26` 也一样灭不了屏（音量键一注入就生效）
  ⇒ 不是权限、不是执行侧，是「电源键」这个码本身被框架忽略
- 改法：`keyevent:26` 那一档不再注入，走 `PowerManager`：亮着 `goToSleep`、睡着 `wakeUp`
  （两个都是 `@hide`，反射调；`DEVICE_POWER` 靠宿主是系统应用）。函数挪成顶层
  （`ActionRunner` 那只类顶到 detekt 的函数条数上限）
- 真机复核：模拟双击电源键 → 日志 `电源键：已请求灭屏（goToSleep）`、`mWakefulness=Dozing`

  会话层边界＝节点边界 ⇒ 阴影四周被裁 —— 破法是**给阴影留出画布**：

### 命名弹窗「聚焦后又失焦」再修一次

- 上一轮只解决了「FrostedDialog 自己收键盘」那一半。另一半是**窗口焦点**：
  两个弹窗交替出现时（收集按键 → 添加按键），新窗口拿焦点晚于 `requestFocus()`，
  焦点给出去又被抽走
- `FocusOnShow` 现在把 `LocalWindowInfo.isWindowFocused` 放进 effect 的 key：
  窗口真正拿到焦点那一刻才抢焦点、叫键盘；之后窗口焦点再变化还会重来一遍

### 命名弹窗：把「叫键盘」整套收回 `FocusOnShow`（弹窗消失后不再拉起键盘）

用户口径：「我说的是**添加按键成功后**的命名弹窗，你现在这样改弹窗消失又把键盘拉起来了」。

- **先纠正一个错判**：上一轮把「叫键盘」挪进输入框（`IconInputView`），理由是「弹窗是另一个
  窗口、页面那侧的控制器不认它」。这是错的 —— COUI 的浮层不是 Android `Dialog`，它挂在
  **根 Scaffold 的 `popupHost`**（`COUIPopupUtils.COUIPopupHost`），与页面**共用一棵视图树、
  同一个窗口**，`LocalSoftwareKeyboardController` 两边读到的是同一个对象（库自己在
  `DialogEntry` 里收键盘用的也正是它）。所以叫键盘回到 `FocusOnShow` 这一侧是对的。
- **副作用从哪来**：上一版在输入框的 `onFocusChanged` 里挂了两样东西 ——
  「失焦就抢回来」的看门狗（1.5s 内最多 6 次 `requestFocus()`）与「连叫 3 帧 `show()`」。
  两样都**不认 `show`**：弹窗关掉之后它们还在跑，于是键盘被重新拉起来。
- 现在：
  - `IconInputView.inputFocusBehavior` 只剩一件事 —— 首次聚焦把光标挪到末尾（它手里没有
    `show`，就不该做任何「主动」动作）；
  - `FocusOnShow` 在 `requestFocus()` 成功之后连叫 `IME_KICK_FRAMES = 6` 帧键盘，
    每一轮**先挂起再 `show()`**：`show` 变 false 时 effect 被取消，协程在挂起点抛取消，
    于是关窗之后**一次都不会再叫**（顺序反过来会多叫出最后一帧）。
- 为什么要连叫 6 帧：库的 `DialogEntry` 在 `showState` 变 false 时**无条件** `hide()`
  ——「收集按键」刚关、「添加按键」刚开这两件事挤在同一帧，只叫一次会被那一下盖住。

### 命名弹窗失焦：**根因是「按电源键收集」**，键盘改由输入框自己守（受 `show` 约束）

用户反馈「还是一样」，这次带了一版录屏 + 系统日志，两个证据一对就清楚了：

- 录屏逐帧（6fps）：`19:17:44` 命名窗露出、**键盘在**（光标就在「按键 1」的末尾）；
  约一帧之后 → **弹窗还在、键盘没了**。
- `logcat`：同一秒 `OplusKeyEventUtil: mIsPowerKeyDown=true`（`19:17:44.029` 按下、
  `.092` 抬起）—— 用户是用**电源键**当这颗自定义键的。

所以链条是：收集到电源键 → 命名窗弹出 → 键盘正常出现 → **电源键在 ROM 自己的处理链上
顺手把 IME 收掉**。上一版只做「打开时连叫几帧」（`IME_KICK_FRAMES = 6` ≈ 100ms），
叫完就没人管了，于是后半程掉下去。这也解释了为什么从菜单点「重命名」从不复现：那条路
不经过物理按键。

改法（`IconInputView` 新增 `ImeGuard`）：

- 输入框多收一个参数 `show: Boolean?`：`null` = 普通输入行（命令页那两栏），不启用守卫；
  非 `null` = 弹窗里的输入框，值为弹窗此刻开没开；
- 守卫是一个**定时看几眼**的 effect（每 6 帧 ≈ 100ms 看一眼，窗口 2s）：
  键盘露着且焦点在 ⇒ 不动；失焦 ⇒ `requestFocus()`；聚焦着但键盘没了 ⇒ `keyboard.show()`；
- **`show` 是唯一开关**：它一变 false 这个 effect 立刻取消 —— 这是上一版「弹窗消失又把
  键盘拉起来」的根治点（当时那段写在纯 `onFocusChanged` 里，手里没有 `show`，
  关窗那 200ms 退出动画期间还在抢焦点）；
- `FocusOnShow` 相应缩回「只负责把焦点交过去」，`IME_KICK_FRAMES` 删除。

为什么不用「盯 `focused` / IME 高度变化」做 key：IME 收放动画每帧都在变，effect 会被反复
取消重启，最后谁也不确定跑没跑完。固定窗口 + 定频检查更可控。

### 「这颗键不能添加」改成消息条；提示条整体挪到浮层之上

- 用户口径：被拒的理由**不要写在 dialog 正文里**，走消息条。`CollectKeyBody` 现在只剩
  「按下想添加的按键 / 正在等待按键…」两句话，高度恒定、按错也不会跳一下

  这句老结论仍然成立
- 所以 `PageContent` 的提示条改挂到 **`popupHost` 槽、排在 `COUIPopupHost()` 之后**

- 副作用：确认窗（清空配置 / 删除按键）开着时，提示条也会浮在它上面。这是想要的
  （回执本来就该压在最上层），且提示条只占底部一条，不遮按钮

### 耦合性复核：本轮 7 个文件的跨层影响

用户口径「检查一下工作区变动的代码/功能耦合性，此前已多轮降耦，不要破坏规范」。

**脚本口径无回归**：`python tools/audit-coupling.py` → 221 个文件、包级依赖 **30 条边**、
禁止边零越界、包级无环（与本轮改动前同为 30 / 0 / 0）。

**修掉的问题**（都不是「方向错了」，而是「搬了位置却没把配套的让位/前提搬过来」）：

1. **提示条挪槽后丢了底部 inset**（真机可见，`PageContent`）。`snackbarHost` 槽是库自己按
   `contentWindowInsets` 让过位的，`popupHost` 槽不管 —— 而这一页 `contentWindowInsets` 全零。
   照原样搬过去，提示条会沉进手势导航条那一条里（`HINT_BOTTOM_GAP` 的 24dp 是按「槽底=可视底边」
   算的，合计 32dp）。现在槽里补 `.windowInsetsPadding(hintInsets())`，只让导航条。
2. **`collectClosed` 的兜底会误放行**（`CollectKeyDialog`）。原实现是「听到键后 600ms 无条件置位」，
   而这个位只在弹窗**重新打开**时才重置 —— 于是「用户自己点遮罩关掉收集窗 → 回调照常置位」之后
   仍开着的那条 effect 到点会再置一次。改法：`onDismissFinished` 里加 `if (collectClosing)` 闸门，
   兜底 effect 到点改为 `if (show) collectClosed = true`（弹窗还开着才说明回调真丢了）。
3. **三处注释还在说旧分工 / 旧层级**，而它们正是「提示条能不能在弹窗里用」这条规则的唯一记录处：
   - `PageFeedback.kt`：「弹窗永远在 Snackbar 之上，那两处各有各的落点」→ 前提已被推翻，
     拒绝理由已走 `hint()`，现在只剩命令执行失败（模块不在前台）那一处；
   - `PageConfirmDialog.hideImeOnShow`：「`FocusOnShow` 会在露出后叫出键盘 / 那边要连叫几帧」
     → 键盘归 `ImeGuard`，聚焦改成等收场；
   - `RenameKeyDialog` 与 `PageEntry` 里各自那句「键盘由 `FocusOnShow` 叫」「挂在 `snackbarHost`」。

**确认「有正当理由、不动」的三条**（已写进 `docs/decoupling.md` 新增的第十节）：

- `ui/screen/PageContent.kt` import 库的 `COUIPopupHost` —— `popupHost` 是 `Scaffold` 给的槽、
  默认值就是它；要的东西在默认值里面，只能改写槽并把默认那几个 composable 自己摆一遍。
  它是库**公开**入口（非反射/内部类），全仓唯一一处在用；库改名时会在这里当场编译失败。
- `ui/screen/binding/BindingList.kt` 读 `overlays.hasOpen()` —— `ui/screen → ui` 本来就允许。
  但要记住 `hasOpen()` 的**口径比它的用途宽**（提示条也算一层浮层）：这一轮拿它做「浮窗开着就别抢
  按键焦点」正合适，下一次做更窄的判断（比如「页面能不能吃按键」）前要先看清。
- `IconInputView(show = …)` 从 `binding/` 传进 `command/` —— 同一层内、脚本不记边。克制的点是
  `command/` 只认识「`show`」不认识「弹窗 / 收集按键 / 收场」；往这里加 `dialogId` /
  `onDismissFinished` / `isCollecting` 之类才会变成真的反向耦合。

**顺带核了一遍时序**：`collectClosed` 不给 `AddKeyDialog` 的 `ImeGuard` 当开关是对的 ——
守卫只跟 `show` 走，`focusReady = false` 期间它本来就会把焦点抢回来、键盘叫出来，只是
250ms 后被退场那声 `hide()` 收走。所以`AddKeyDialog` 这边只改聚焦时机，不动守卫（守卫若也
跟着 `collectClosed` 走，反而是把「键盘被收走后补回来」这份能力也一起关了）。

**基线更新**：`SettingsPage.xxx` 扩展 204 个 / 65 文件 → **215 个 / 67 文件**（这一批新屏文件
