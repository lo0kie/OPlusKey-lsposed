# 应用控制

### 新增：快捷功能里那一格「进程控制」改成「应用控制」

- 那一格点开先是**一层二级菜单**：打开应用 / 结束应用。两档进的是**同一张**挑应用页（搜索、进场定位、右下角确认、空态都沿用那一页）。
- 打开那一档绑成「打开应用」（`app:包名`），结束那一档绑成「结束应用」（`proc:stop:包名`）。绑好之后网格里那一格的小字与图标跟着状态变（`打开应用:微信` / `结束应用:微信`，结束是那颗方块）。
- 「进程控制」那一页**撤掉了**：进程列表、排序方式、下拉刷新、当场结束那套都不再有 —— 那一页能做的事，一页应用列表就够。
- 「启动进程」那一档**删掉了**：它与「打开应用」是同一件事，两格并排只会让人以为两者有区别。配置里残留的旧写法按「认不出」处理，不执行。
- 结束的是**整个应用**（含 `:push` / `:service` 那些子进程），与原来一样是「系统停 → 强杀残留 → 再核实一遍」三步，只是不再先绑到按键上才能试。
- 这一格不是一条动作：多条命令与系统场景里它仍落成「打开应用」那一步。

### 修改：「选择应用」页的失效应用开关按这一趟分档

- 「显示失效应用」**只在「打开应用」那一趟**出现在菜单里（默认关 = 默认不显示）；「结束应用」那一趟没有这一项，**一律全部列出** —— 停掉一个没有启动图标的应用正是它的用处。
- 行尾的「不可打开」标签**只在「打开应用」那一趟**挂着（红色小标签）：那一趟可能把这类应用藏起来，看得见的时候得知道点下去会失败；「结束应用」那一趟不挂 —— 停掉一个没有启动图标的应用正是它的用处。
- 「打开应用」那一趟藏着失效应用、剩下又都打不开时，空态那句话指回菜单里那一项。
- 点确认时仍会拦一次「此应用无法打开」（打开那一趟）；结束那一趟不拦。

### 修复：两个显示开关「按了没反应」（结束一趟之后必现）

- 现象：先进「结束应用」那一趟、再进「选择应用」，「显示失效应用」拨了没反应。
- 根因有两层：
  · 这两个开关以前是**取清单的输入**（`includeAll` = `显示系统应用 || 显示失效应用`）：拨开关 = 换一种查询 + 把清单打回加载态 + 换一份缓存。这套账有三笔跨趟残留（上一趟的取法 `lastMode`、缓存是哪一档查的 `cachedAppsIncludeAll`、以及重查失败那次没人看得见的日志），任一处错位就是开关失效；
  · 「结束应用」那趟的 `stopApp` **没被算进取法**，它拿到的仍是「只有启动图标的那批」——「一律全列」只能全列出手上那点东西；而 `stopApp` 还是个普通 `var`，`shown` 那个 `derivedStateOf` 读着它，缓存会把「结束那趟的算法」带到下一趟。
- 现在：清单**一次取全**（有启动图标的 + 模块 + `getInstalledApplications` 的其余应用），两个开关纯过滤（`byDefault` / `launchable` 两档事实），拨开关不查盘、不重查、不换缓存；`stopApp` 改成 compose 状态。全量取法付得起这笔账，是因为「点不点得开」从「逐包 `AppEntry.resolve`」换成了「一次问全机」（`AppEntry.launchablePackages`，判据仍是同一份 `isLaunchable`）。
- 副作用（有意）：结束那一趟现在真的能列到**没有启动图标**的应用了（以前那批根本不在清单里）。

### 修改：打开 / 结束两档的选中与图标

- 两档只认自己那一族：键上绑的是「结束应用」时，进「打开应用」那一趟不再把它点亮、也不再滚到那一行；反过来同理。
- 两行的图标换成一对：打开是播放三角、结束是方块；网格里那一格也按绑的是哪一档画（绑到某个界面或快捷方式时仍画它们自己的标记）。

### 新增：选中那一行加一圈内边框

- 「选择应用」与「选择界面」两页里，**当前选中那一行**外面加一圈主题色内边框（2dp）。行尾那颗勾/圈说的是「选中了」，几百行里那一颗太不起眼，扫一眼看不出自己挑的是哪个。
- 四角是**超椭圆**（squircle）：COUI 的卡片圆角全是 squircle，用 `Modifier.border` + `RoundedCornerShape` 画出来的正圆角在四角处会伸到卡片轮廓外、被裁掉一截（真机反馈「圆角处不完整」）。改成用库的 `addSquircleRect` 拼路径自己画，并整体往里让 2dp（贴边画会被抗锯齿吃掉外侧一半），半径同步减这一档，内外两条曲线才同心。
- 选中那一行的**标题也跟着上主题色**：内框管「这一行是当前这个」，标题管「读哪个名字」 —— 几百行里先落到眼睛的应该是字。
- 两页共用同一份（`Modifier.selectedRowRing`）：同一种状态在两页长得不一样，用户会以为选中的东西不同。

### 修复：进场定位「少了半截」（目标行被顶栏/搜索带压掉）

- 现象：进「选择应用」自动滚到已绑定的那一行，那一行被固定搜索带压掉一截（真机压掉 29dp）。
- 根因：这个库折叠顶栏是「**缩标题、不缩外壳**」—— `heightOffset` 已经拉到 `heightOffsetLimit`，底下那条固定搜索带仍停在**展开位**。定位却按 `collapsedHeaderHeight`（展开高 − 折叠量）算落点，于是少让了整整一段折叠量（本机 193px）；`GRID_GAP / 2 + PAGE_TOP_PADDING` 那 14dp 只把这个错抵消掉一小半。
- 现在：落点按库的两个**槽位常量**算（展开 / 折叠各一档），不读实测高度。中间那几版分别踩过「`currentHeaderHeight` 随折叠变（展开 684 → 折叠 491），按它算落点会多让一整段折叠量」（真机反馈「滚动距离偏多，且不止首次」），以及「`scrollToItem` 返回时布局还没重跑，读 `layoutInfo` 纠正会多滚一整屏」。现在的做法：常量定落点（`TopAppBarDefaults.ExpandedHeight` / `CollapsedHeight` + 系统栏 + 搜索带），滚完等一帧再按实测 `layoutInfo` 只往上收一次（`settleRowBelow`）。两页都改了。
- 日志多两个数：`定位到已选：index=… 遮挡=… 目标=… 落点=…`，下次一眼能看出差多少。

### 修改：顶栏主标题 / 副标题分工

- 主标题不再恒为「选择应用」，改成**这一趟要干的事**：结束那一趟是「结束应用」，打开那一趟是「打开应用」。
- 副标题只留一句「已选择: xxx」（还没选时是空串）。原来副标题写的是同一个词，主副两行读起来像同一句话说了两遍。
- 判据是 `picker.stopApp`，与列表过滤、行尾标签、确认时的拦截同源 —— 四处各判一次就会有一处写反。

### 修改：消息提示条带上动作前缀

- 「已绑定」回执原来只写应用名（`已绑定「微信」`），看不出这一下绑的是「打开」还是「结束」。现在走 `actionTitle`（与步骤行、执行时提示同一支实现），产出 `已绑定「打开应用:微信」` / `已绑定「结束应用:微信」`。
- `boundNotice` 里三档应用动作的差别只有「应用名从哪个字段取」，抽成 `appPkgOf` 之后共用**一次** `actionTitle` —— 三处各写一遍等于「怎么念一个动作」又多出三份实现。
- `tools/audit-arch.py` 的 `actionTitle 调用点` 规则从 `= 2` 改成 `= 3`（执行时提示 / 步骤行 / 绑定回执）：这条记账本就该跟着设计走，而不是把代码拧成满足旧数字。

### 修复：结束应用失败时只说「这次没成功」

- `ProcessController.perform` 的回调从 `(Boolean)` 改成 `(CommandFailure?)`，把**具体是哪一档失败**透传上来（起不来 `su` / 权限被拒 / 命令没跑成）。
- 失败档随后交给既有的那套 `CommandFailure` 话术报出去，用户知道该去授权、还是该看应用在不在 —— 不再一律「这次没成功」。日志也跟着带上档位（`proc：proc:stop:… 没成功（SHELL_NO_ROOT）`）。
- 为什么原来只剩一句话：`exec` 的两个出口（`onFailure` / `onTip`）都被拍成了同一个布尔，具体档位在那一步就丢了 —— 上层再想说清楚也没料。顺带把「只回一次」收紧成 `AtomicBoolean`（调用方里有直接拿去弹提示的，回两次就是两句提示）。

## 导入配置：先挑盖到哪一份

### 新增：导入时弹「覆盖配置」选择器

- 文件校验通过之后不再直接「插在最末」，先弹一层选择器：列出**已有的每一份配置**（含「默认配置」），最末一行是「新增配置」。
- 单选 + 确定：点一行只是「选中」，再点「确定」才作数。覆盖是一整份配置（连同命令库）被换掉，代价与「删除配置」同档 —— 点一下就走太轻，中间得能反悔（点别的行 / 点取消）。
- 还没选就点「确定」：按钮灰着但仍可点，点一下报「先从列表里选一份配置」—— 灰着却按不出声，最容易让人以为界面坏了。
- 「新增配置」到顶（除默认外已有三份）时那一行同样灰着但仍可点，点了报「最多三份配置」。它与上面几行之间用一条**加深带**断开：上面是「盖掉哪一份」（替换已有的），这一行是「另起一份」，两类动作不是一件事 —— 一条同样粗细的细线读起来还在同一组里。加深带的颜色与粗细与浮层菜单组间那条同一档（`DropdownDefaults.PopupGroupDividerThickness` + `MENU_GROUP_LINE_*_ALPHA`）。
- 「读不出来的那一份」**不进这张列表**：它没有可保留的名字与位次（`importInto` 按 `readOf` 拒绝覆盖），列进来只会让用户选中之后得到一句「导入失败」。清理它仍走「切换配置」菜单里那条删除（`ProfileBrokenDeleteDialog`）。

### 新增：覆盖之前再问一句

- 在选择器里点「确定」选了某一份之后，**再弹一层确认窗**，正文点名要盖掉哪一份（「**默认配置**」这份配置的内容与命令都会被换掉，且不能撤销）。
- 两层窗不叠着开：选择器先收场（`onDismissFinished`），确认窗才置上 —— 同帧开两个会叠在一起，后一个的磨砂底压在前一个面板上。
- 确认窗正文里那个名字经 `escapeEmphasis` 转义：配置名里带 `*` / `-` 时不会被当成加粗或项目符号。

### 新增：`ConfigProfiles.importInto`（core）

- 与 `importAs` 的差别：目标是**一份已有配置**，内容整个换成导入的，但**换内容不换名** —— 保留那一份自己的 `profileName` 与 `profileOrder`，只把 `profileId` 换成新的（导入文件里带着别人的 id，照抄会撞车）。
- 两段一起成、或一起不动：先落命令库、再落主配置；任一步失败就把这一槽还原成原样（走 `importAs` 那条「删槽」的路会把那份旧配置丢掉）。
- 变量表换成空表（与 `importAs` 同一口径）：导入的那套不该带走别人的计数。
- **覆盖当前生效的那一份**时这一层只负责把文件写对，不广播、不动界面状态 —— 那一半交给调用方走通用写入通道（`write`），与「切换配置」同一条收尾。
- 回执分开说：「已覆盖「默认配置」」/「已导入为「导入配置」」—— 两件事不再共用一句。

### 修改：导入那份的名字带序号，从 1 起

- 「新增配置」这条路落的名字一律带号：「导入配置 1」「导入配置 2」……`importAs` 里那个 `seq` 起点从 2 改成 1，第一份也加。
- 以前第一份不带号、第二份才从 2 开始，列表里并排放着「导入配置」和「导入配置 2」—— 一眼数不出这是第几份，两行的差异看着像「一个特殊、一个普通」。
- 打底名字仍来自文件里的 `profileName`（空则「导入配置」），序号一律另补：文件叫「我的配置」，落下来就是「我的配置 1」。覆盖（`importInto`）不涉 —— 那条路**换内容不换名**。

### 修复：选了目标、点「确定」没反应（确认窗永远不弹）

- 现象：覆盖配置的选择器里选中某一份、点「确定」，窗直接关了，确认窗没弹、什么也没写。
- 根因：选择器的几样临时状态（选中项、待弹的确认窗、列表、是否已满）都挂在 `remember(pending)` 上，而「确定」那一下**先把 `pendingImport` 清掉**（窗从这一刻开始退场）。那一帧重组，`remember` 的 key 变了，四个状态**全部重建** —— 刚写进去的「接下来弹哪张确认窗」当场变回 `null`，`onDismissFinished` 读到的正是这个新值，于是什么都不弹。`remember` 的 key 一变就丢值，而这里恰恰要在 `pending` 变 `null` **之后**还读得到它。
- 现在：状态收进一个不带 key 的 `remember { ImportTargetState() }`（页面这段时间只组合一次这一支，对象不会重建）；「每次打开重读列表、清掉上次的选中」交给 `LaunchedEffect(pending)`，`pending` 变 `null` 时直接返回 —— 退场动画还在用手上那份列表，清空会闪一下白。
- 同一个坑对 `selected` 也成立（清空后行上的勾会当场消失），一并治了。

## 首页「模块状态」卡：关着时补一句「点击启用此处模块」

- 这一块**整块就是开关**，可界面上原本没有任何记号说明这件事 —— 大字只写「已关闭」，用户看到的是一个「关掉的状态」，不会想到去点它。现在在说明那行下面补一行「点击启用此处模块」（正文那一档字号、字重加半档、主色，与卡里提示段那颗「查看」同一族观感）。
- 只在**点得动**时出现：链路没就绪（宿主侧没跑 / 注入侧没报到）或配置只读时不写 —— 说了却点不动比不说更糟。判据收在 `activationToggleable` 一处，与整块那个 `onClick` 同源（原先 `linkReady && !configState.readOnly` 是就地写两遍的写法）。
- 这一行的来去会让**整张卡**高一档，所以走 `VISIBILITY_ENTER` / `VISIBILITY_EXIT`（淡入 + 纵向展开 / 淡出 + 纵向收缩）：硬切就是卡片一秒钟跳一下，而开关自己切状态时本来就有一条 200ms 的颜色过渡，高度这一下得跟上同一条节奏。
