# 2026-10-15 · 设置页与配置一批改动

### 修：从模块页首页返回设置 / 桌面没有预测动画（2026-10-15）

- 返回回调改成**按需挂**：只有「子页 / 浮层 / 露着宿主原版页」这几档才在宿主上注册
  `OnBackInvokedCallback`，首页、无浮层时一概不挂
- 由此首页那一退**交还给系统**：关掉整个设置页的跟手缩放与「露出下面那一层」由系统自己做（下面那两层的事只有系统能做，模块画不出来）
- 判据由页面回报：进出子页 / 浮层开合时页面通知 hook 侧重算一次；「露出宿主原版页」与切回模块界面时 hook 侧自己重算
- API 33 及以下不启用这套（那些版本没有预测返回），行为与之前一致
- 日志：新增 `返回回调：已挂上 / 已摘掉` 两条（`w` 级），进页那条汇总里也报此刻挂没挂

### 修：「选择应用」页里已选的应用被开关藏起来还留着选中（2026-10-15）

- 「隐藏失效应用」「显示系统应用」任一翻转后对一次账：已选中的那个应用不在**这一档过滤之后**
  的清单里 ⇒ 清空选中（右下角那颗 ✓ 跟着收起，不会再把一个看不见的应用写进绑定）

### 浮层菜单 / 底部工具栏 / 右下角 FAB 挂上「磨砂」（2026-10-15）

- 机制：库没有现成的浮层模糊（`OverlayListPopup` 只有 `enableWindowDim`，文档与 jar 里都没有窗口级
  `BlurBehind`），所以复用项目已有的那一套 —— 页面内容层 `layerBackdrop` 记录 + `Modifier.frosted`
  取样（顶栏一直在用）。取样方都在那个记录层**之外**：浮层画在 Scaffold 的 `COUIPopupHost`、工具栏挂在 `layerBackdrop`
  那个 Box 外面 ⇒ 不会自取样（自取样 = RenderThread 栈溢出，真机崩过一次）
- 取样源记在页面上（`SettingsPage.pageBackdrop`），四个浮层菜单 + 工具栏 + 二级浮层直接取，不再一层层传参
- 浮层面板：库 `ListPopupContent` 是不透明底（`couiColorSurfaceTop`：浅 `#FFFFFF` / 暗
  `#333333`）＋ 12dp 圆角且**不裁子级** ⇒ 磨砂只能画在面板**里侧**并自己按 12dp 收边；底色改用库那一对（主题里没有
  `surfaceTop` 这一档，`surfaceContainerHighest` 暗色只有 `#252525`，比库原生还暗 ——真机反馈「暗色下底色太暗」）
- 行底让位：`MenuRow` 把行的 `containerColor` 抹成透明（未选中行本来就与面板同色，抹掉不改观感，改的只是「谁能盖住谁」）
- 分隔（同日真机反馈「暗色下看不清」）：行内细线暗色走**亮**线（白 14%）、浅色仍是黑 10%；组间那条槽暗色加深到黑 32%
- 底部工具栏：`FloatingToolbar` 去掉
  `compositeOver(surface)`（那一步把它压成不透明实心，正是原来「磨砂看不见」的原因）、`showDivider = false`（那圈不透明描边与半透明底互斥），色取
  `surfaceContainer`，alpha 按比例缩到 [FROSTED_SURFACE_ALPHA]
- 修工具栏外面那圈糊边：库内部是 `modifier → padding(outSidePadding) → … → squircleBackground`，磨砂挂在 `modifier`
  上就画的是**连留白一起**的整块矩形 ⇒ 改成自己先 `padding(OutSidePadding)` 再挂磨砂，同时把库的 `outSidePadding` 传
  `0.dp`（留白只留一次）
- 修暗色下工具条发亮：alpha 只能**按比例缩**、不能 `copy(alpha = …)` 整个换 —— 库深色板的 `surfaceContainer`
  是半透白（白 10%），整个换成 0.82 就成了「白 82%」的亮胶囊（浅色板里它是实色白，替换看不出来所以之前没暴露）；缩放后暗色 ≈ 白 8%、浅色不变
- 修工具条阴影被磨砂裁掉：`drawBackdrop` 内部是 `placeWithLayer(clip = true, shape = 圆角矩形)`，库自己的 `dropShadow`
  挂在那层**里面**、而阴影本来画在形状外 ⇒ 被裁得一干二净；改成库的 `shadowElevation`
  置零，按库原样（`radius 10dp / 黑 10%`）在裁剪层**外面**补一层同样的阴影
- 右下角那颗 FAB（「选择应用」的 ✓ 与「按键绑定」的「新增命令」）：样式收进新的 `PageFabButton`
  （磨砂 / 形状 / 底色 / 阴影一处一份，两个调用点不再各写一遍）—— 形状仍是库默认圆、底色是 **主题原色**

### 「选择应用」页：清单没到手时不给保存 + 把起不来的活动挡在「入口」之外（2026-10-15）

- 右下角那颗 ✓ 的显隐从「有选中就出现」改成「有选中**且清单已到手**才出现」—— 它是本页唯一的保存入口，藏起来就等于不允许保存（用户口径「加载应用列表时不允许保存，隐藏掉 FAB」）
- 起因：清单还在查（或查失败又没缓存）时 `apps`
  是空的，点 ✓ 取不到那一位应用 ⇒ 两道拦人的检查（「此应用无法打开」/「不支持以小窗口打开」）会因为 `app != null`
  这个前提不成立而双双跳过，等于把「还没核对」当成「没问题」照写下去
- `AppEntry.resolve` 收严三处（列表那枚「可以打开」与 `app:` / `window:` 动作共用它，两边一起修）：·
  **没有代码的包**（`android:hasCode="false"` ⇒ `FLAG_HAS_CODE`
  为 0）一律判不可打开 ——这类纯资源包声明得了组件、却一个都起不来（类不在包里）· 第三层（「任意 `ACTION_MAIN`
  活动」）**排除带 `android:permission` 的活动**
  —— 那种活动要调用方持有（多半是 signature 级的）权限，而本模块零权限，起它就是 `SecurityException` · 第三层再**排除
  `android:excludeFromRecents` 的活动**
  —— 那是悬浮面板宿主 / 磁贴设置页这类辅助活动的写法（「不进最近任务」正说明它不是「打开这个应用」的入口）
- 查证结论（用户报「Android 系统打不开但是没有被过滤」的真因）：那一行**不是** `android` 包，是
  **`oplus`**（`/system_ext/framework/oplus-framework-res.apk`，OPPO 的框架资源包，**标签同样是「Android 系统」**）。`android`
  那行反而被正确滤掉了（它全包只有 `SystemUserHomeActivity` 一个 `MAIN` 活动，且 `enabled=false`，`am start` 直接报 does
  not exist）。`oplus` 漏网是因为它有 `TileLongClickActivity`（`MAIN` + `QS_TILE_PREFERENCES`、`exported`、带
  `BIND_QUICK_SETTINGS_TILE`，而整包 `hasCode=false`），被第三层当成了「这个应用的入口」
- 查证结论二（同日「AI语音摘记也打不开」）：那是 **`com.coloros.accessibilityassistant`**
  （`application-label='AI VoiceScribe'`），整包**没有** `MAIN`+`LAUNCHER` 的活动；漏网的是
  `floatpanel.MainActivity`（悬浮面板宿主：`excludeFromRecents` + `resizeableActivity=false`），同样被第三层当成了入口

### 多条命令的「一次只跑一条」闸：从按名字改成按「有没有链在跑」（2026-10-15）

- 现象：连着触发两条**不同的**多条命令时，两条链会**交错**
  —— 第 2 条的第 1 步插在第 1 条的第 2 步前面（间隔越长的链越明显）
- 根因：闸的注释写着「同时只跑一条」，实现却是**按命令名**挡（`runningSerial`
  是个名字集合）——两条名字不同的命令谁都挡不住谁。同名重入挡得住，异名交叉挡不住
- 改成两道：
  - 顶层（`depth == 0`）**非空即挡**：只要 `runningSerial` 里还有人，新的顶层触发就跳过；嵌套（一步写
    `cmd:<另一条>`）不算新的一次触发，不挡。只看顶层还不够 ——嵌套那条还在跑、外层已经结束的那段尾巴同样非空，这一条正好把那段盖住
  - 任何深度仍按名字挡一道，盖住 `cmd:` 自引 / 互引（手改命令库才写得出来的环）
- 被挡下的这一下现在会**说一声**：复用 `CommandFailure.OVERLOADED`（「上一条命令还没跑完，稍后再试」）弹一次 + 落 `w`
  日志 —— 闸把用户这一次手势吞掉了，不能连个动静都没有
- 顺带补一处会让闸**自锁**的漏：`postDelayed`
  的返回值原来没人看，主线程 Looper 要退时那一枪排不上、占位就留在集合里。只按名字挡时漏一个只死它自己；改成「非空即挡」之后会锁死**所有**
  多条命令，所以要在排不上时显式归还
- 已知、本轮没动：
  - 一步写 `cmd:<另一条多条命令>` 时**不等它跑完**就往下走（它那条链自己 `postDelayed`
    续步）。步骤菜单只给内置动作、写不出这种一步，只有手改命令库才会出现
  - 设置页「测试命令」跑在 `:ui`
    进程、按键链跑在宿主主进程，两处各有一份闸、互相看不见 ——跨进程要共享得引入文件锁或广播，只有「一边跑链一边点测试」这一种场景会撞上
- 取证：`compileReleaseKotlin` + `assembleRelease`（R8 + lintVital）全绿；装机后库里的 `apk_path`
  与真机当前路径一致（`enabled=1`、scope 不变）

### 「明明抬手了还判长按」：抬手时摘掉长按那一枪 + 长按下限抬到 200ms（2026-10-15）

- 现象（用户报）：单击延迟与长按延迟都设成 100ms 时，按一下触发的是**长按**，单击不触发
- 拆成两笔 —— 一笔是设计使然，一笔是真缺陷：
  - **设计使然**：单击成立的条件是**按住时长 < 长按延迟**（与单击延迟无关 —— 后者只管「抬手之后还等多久看有没有第二下」）。100ms 落在人手一次自然按压（80~150ms）里，这一档下正常按一下就是长按。`2026-10-14`
    那一节已经记过这笔代价（「界面不拦，注释里写明」）
  - **真缺陷**：长按那一枪只在到点时读一眼 `sawFirstRelease` 决定响不响，而那次读**跨线程**
    （输入线程写、主 looper 读）—— 读到陈旧值就是「明明抬手了还判长按」。长按延迟压到 100ms 时，抬手与到点只隔几毫秒，正是这种读最容易失手的位置；本类注释原来把它记成「偶发误判长按」
- 修法：把那一枪的 Runnable **存下来**，抬手（`onKeyUp`）与 `reset` 都 `removeCallbacks`
  摘掉它 ——「到点之前就没了」是确定的，不依赖那次跨线程读。顺带把 `reset`
  的 KDoc 坐实：原来那句「reset 会取消那个还挂着的长按计时器」只靠栅栏间接成立
- 给跨线程字段补 `@Volatile`（原来只有 `lastDirectSingleAt` 有）：输入线程写 `sawFirstRelease` /
  `pressAt`，主 looper 那一枪写 `longPressAt` / `longPressFired`，两边都写也都读；`doubleFired` 不加（只有输入线程碰它）
- **残留（写清、没修）**：`check → act` 那几段仍无锁，极端竞态下「既判长按又判单击」只是变小、
- 界面：「长按延迟」那一行的说明定成「多久算长按，比它短算单击」—— 按不出来时用户第一个怀疑的就是这个数，只点这一句；写全「这一档已短于人一次自然按压」太长，会把行撑成两行、与旁边几行也不齐
- **长按阈值下限 100ms →
  200ms**（`KeyConfig.MIN_LONG_PRESS_MS`）：200ms 已高于人手一次自然按压（80~150ms），任何一档下「正常按一下」都不会被判成长按 —— 直接堵掉「怎么点都是长按」这个组合，不必指望用户先踩一次再回头看说明。`2026-10-14`
  那一节「界面不拦、只把代价讲明」的处置随之作废
- 副作用（有意）：读配置时按新下限钳制 ⇒ 存着 100ms 的老配置会被抬到 200ms
- 取证：`compileReleaseKotlin` + `assembleRelease`（R8 + lintVital）全绿；装机后库里的 `apk_path` 与真机当前路径一致

### release 体积：dex 压进 zip，3.34 MB → 1.59 MB（2026-10-15）

- 先量账：`classes.dex` 占全包 95%（3050 KB / 3257
  KB），而且是**「不压缩」存进去的**（AGP 默认，为的是让 ART 能 mmap 共享）；其余是 `resources.arsc` 64 KB、res 10

  1,663,783 字节（−50%）**
- 代价：那份 dex 不再 mmap 共享，改由加载它的进程各解一份；而 LSPosed 会给模块传 `preLoadedDexes`
  （框架自己的缓存），真机上不一定走到解压这一步 —— **装机后待整机重启确认模块照常注入**。旁证：在用的

  `com.luckyzyx.luckytool` 与我们改前一样是不压缩
- 顺带核过：包内未压缩的那几条（`resources.arsc`、4 个 `.so`、baseline profile）仍按 4 / 4096 字节对齐，
  `META-INF/xposed/` 三件套与清单原样
- 看过后没动的：`META-INF` 里 5 份第三方 LICENSE.txt（50 KB 原始 / 18 KB 压缩）是署名文本；x86 / x86_64 两个 `.so`（18
  KB）删了模拟器就装不上；res 侧 `isShrinkResources`
  本来就开着、已无可剪；dex 里 58% 是 Compose、10% 是 COUI，R8 已剪过，唯一还能砍的是 markdown 那套渲染（属回退功能，不做）

### 三处加固：`cmd:` 成环拦在保存、写盘补 `fsync`、应用图标改按需取（2026-10-15）

- **`cmd:` 成环**：新增 `Command.referencedNames()`（把「这一条引用谁」收成 `referencedName` 一处）与
  `Command.cyclePath(start, library)`（从待存的那条出发走引用图，走得回踩过的名字就是环）。界面侧的判据与保存**共用**
  `draftToLibrary()`
  那一份「草稿 → 存库后的库」——两处各算一遍的话，判的与存的就不是同一件事（改名会把引用一起挪、环也跟着变）。表现与重名同一套：名称那格出红字「命令引用成环：A
  → B → A」，保存按钮一起禁掉
  - 成环的害处不是卡死（执行侧有 `MAX_COMMAND_DEPTH = 4`
    兜底），而是**副作用重复**：整条链会一路跑到深度上限才停，写 shell 的那种动作会真跑满 4~5 遍
  - 逻辑用等价实现过了 10 个用例：自环 / 二环 / 三环 / 无环 / 死引用 / 单条正文互引 / A 指向既存环 / 正文里含 `cmd:`
    字样（不算引用）/ 步骤带空白（仍算引用）/ 多条引用自己
- **写盘补 `fsync`**：`writeAtomically` 原来是「写 `.tmp` →
  rename」。rename 只保证「名字换过去」原子，不保证被盖住的内容已经落盘 —— 掉电时可能落成「名字换了、内容还是空的」，正是
  `Load.Unreadable` 那一档。现在写完 `fd.sync()` 再 rename（与 `android.util.AtomicFile`
  同一步；只 sync 文件、不 sync 目录）
  - 写盘线程**保持不变**（仍在调用线程上同步写）：`SettingsPage.write`
    的契约是「落盘成功才提交状态、才广播」，改成异步会打断这条因果链、还要动十来个调用点；一次 `fsync`
    是几毫秒、且都在用户动作之后，与 `SharedPreferences.commit()` 同一条路数
- **应用图标改按需取 + LRU**：`LaunchableApp` 不再带 `icon`，查列表只记包名（原来 `entry()` 对 200+ 个应用逐个
  `loadIcon`）；`AppIcon` 在**滚进视口**时才问一次 PackageManager，取到的记进 48 槽的 `LinkedHashMap(accessOrder)`
  LRU，滚回去命中缓存、不再跨进程问第二轮。省下的是查列表那两百多次跨进程调用与一批常驻
  `Drawable`（光栅化本来就只在每项自己的组合里做）
  - R8 侧核过：匿名子类 `AppPickerKt$appIcons$1` 与它的 `removeEldestEntry` 覆写都保留（`mapping.txt` 在位、`usage.txt`
    里没有它）
- 取证：`compileDebugKotlin` 绿；注入侧依赖禁令复核无命中（`inject/`、`core/` 与两个源集的 `core/` 副本）；
  `assembleRelease` 绿；装机后 sha256 与本地包一致，库里 `apk_path` / `enabled` / 作用域不变。
  **待真机验**：成环时的红字与禁用按钮、图标按需取之后的滚动观感（滚回去是否还复用缓存）
