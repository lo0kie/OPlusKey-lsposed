### 首页：宿主服务未拉起时整页禁用

- 首页新增「宿主侧模块有没有加载」的检测：判据是**模块自己报活**（`ACTION_HOST_SERVICE_UP`），
  不是查宿主那支侧键服务 —— 那是宿主自己的常驻服务，**系统会自己把它拉起**，服务在跑 ≠ 模块在跑
- 进首页时先发一句「在不在」（`ACTION_HOST_SERVICE_QUERY`，报活广播是一次性的、可能已错过），
  3 秒内没有回音就判为未加载；之后不再轮询，模块起来时那声报活会把提示收掉
- 未拉起时**整页禁用**（含「启用按键绑定」主开关行本身，以及顶栏 ⋮ 菜单里动模块运行时的那三项），
  屏幕底边挂一条 COUI `Snackbar`（常驻、无关闭按钮）说明该怎么办
- Snackbar 的宿主挂在页面容器那一层、只对首页生效：它要的是「底部对齐、不随内容滚动」的位置，
  而首页自己整个是滚动容器
- 提示文案：模块未被正确加载，正在等待系统启动
- 服务起来时由宿主进程广播一声（`ACTION_HOST_SERVICE_UP`），设置页收到即把提示收掉、解除整页禁用 ——
  不轮询 `getRunningServices`；首页只在进页时查一次（服务可能在本页组合之前就起来了）
- 弹提示带**去重**：首页被切走再回来会重新组合，不去重会叠出第二条 Snackbar
- 修：主开关关掉后**把自己也禁用了**，再也开不回来 —— 它的 `enabled` 只该看「宿主侧的模块在不在」，
  不能吃那个含它自己的总闸（其余控件照吃）
- 顶栏 ⋮ 菜单里那一项由「重启模块」改叫「重启服务」（含成功提示与日志）：它只是杀宿主主进程，
  **不会**重新加载 system_server 里那份注入 —— 叫「模块」是误导
- 菜单里的「打开默认界面」与「关于模块」两项**不禁用** —— 模块没生效时前者是唯一的逃生口

### 修复：小窗打开无效（`window:<包名>` 按下去什么都不发生）

- 根因：`startZoomWindow` 的 Bundle 里没带窗口模式 —— 空 Bundle 时服务端把它当**普通启动**，
  应用照样开但不是小窗（真机对照实验：同一组件不带 extra 全屏打开、带 `extra_window_mode = 100`
  起小窗，两个都返回 0）。修法：Bundle 里带上 `extra_window_mode = 100`（`WINDOWING_MODE_ZOOM`），
  两个常量抄自 SystemUI 里那个能用的调用方 `ScenarioAssistantNavigationImpl#startActivityByZoonWindow`
- 返回值**不能**判成败：起没起成小窗、退没退成普通启动，返回的都是 0；只有负数才是错误码
  （组件名写坏实测 -92）。所以降级条件收紧成「返回值 < 0」，其余一律当「已发起」——
  按「0 = 失败」降级会把好不容易通的路径再破坏掉
- 上一版「前台转小窗」用的 `startMiniZoomFromZoom(int)` 是这台 ROM 上的**废接口**：
  全量扫过 SystemUI（9 dex）、桌面 OplusLauncher（7 dex）与设置侧，除框架自身的 AIDL 门面外
  没有任何调用方，原型还是 `void`；探针把 `startWay = 1 / 2 / 7` 各调一遍均无可见变化。
  已改走同一条小窗接口，目标换成 `getTopActivityComponentName()` 取到的前台活动
- 「前台转小窗」= 取前台包名 → 复用「小窗打开」那条（入口 activity + `extra_window_mode`）
- 真正的关键一步是 `FLAG_ACTIVITY_MULTIPLE_TASK`：只带 `NEW_TASK` 时，如果目标已经就是前台那个应用，
  要么被判成 `START_DELIVERED_TO_TOP`（`3`）交给栈顶那份实例消化、屏幕不动，要么另开出一份**全屏**
  实例（`windowingMode=1`）—— 看着像「开了但没成小窗」。补上 `MULTIPLE_TASK`（合起来 `0x18000000`）
  才会真的另起一个任务、窗口模式才落得下（真机逐组合对照）。代价：小窗里是新起的一份实例
- `startZoomWindow` 返回 `3` 时仍留一步兜底：先发 CATEGORY_HOME 回桌面、延迟 400ms 再起一次
  （`MULTIPLE_TASK` 在场时正常走不到这一档）
- 查「有没有真起成小窗」只能看 `OplusActivityManager#getAllTopAppInfos()` 里的 `windowingMode`
  （`1` = 全屏，`100` = 小窗）—— 返回码和截图都会骗人；早先就是漏了这一列，把「重开了一份全屏实例」
  误判成「前台转小窗走不通」
- 已排除的几条（都不通）：`startMiniZoomFromZoom`、`toggleFlexibleWindow` 两个 type、
  `startFlexibleWindowForRecentTasks`（分屏）、`WindowContainerTransaction.setWindowingMode(100)`、
  桌面的「带几何启动」配方（`LaunchScenario`/`LaunchFlexibleTaskId` + `calculateFlexibleWindowBounds`
  + `setExtraBundle`：链路全绿、服务端不认这个调用方）
- 系统的「交换应用」也挖穿了（记在 `docs/device-findings.md` §17.6.2）：对小窗任务发事件码 2004 →
  `FlexibleWindowManager#notifyFlexibleTaskEvent`（`oplus-framework.jar` 里的类，这层无权限闸）→ 服务端
  `handleFlexibleExChange` 把「小窗 ⇄ 全屏」两份任务互换。它要求**另有一份不同包的小窗在场**，抄不过来；
  「原地收现有窗口」另有正门，见下面那节
- 真机已验：`设置` / `mark.via` 在前台时按上面配方都能收成小窗（`windowingMode=100` 且稳定停住）；
  「交换应用」也用同款调用复现成功（全屏 ⇄ 小窗互换）

### 改进：前台转小窗改为「原地收」，不再另起一份实例

- `zoom:mini` 主路换成系统的 recents 正门（`startActivityFromRecentsForFlexible(taskId, options)`）：
  服务端直接把**那份已存在的任务**改成小窗 —— 一步到位，taskId 不变、界面状态全留
- options 里窗口模式那个 key 是点号的 `android.activity.windowingMode`（不是 `extra_window_mode`）；
  `mZoomLaunchFlags = 2` 开出来才是**展开**的普通小窗，给 `32` 会开成右上角**收起**的最小化窗
  —— 两个 key 的坑见 `docs/device-findings.md` §17.6.3
- 起完 350ms 核一眼那份任务的 `windowingMode` 是不是 `100`，不是才退回原来那条「按包名另起一份实例」
- 这条**没有转场动画**（改窗口模式，不是一次启动）。有动画的走法是「先挪出栈顶再 `startZoomWindow`」，
  但要多回桌面一步，实测权衡后没采用 —— 四条路的量化对比见 §17.6.4


### 修复：小窗打开不再多开实例（`window:<包名>`）

- 去掉 `startZoomWindow` 里的 `FLAG_ACTIVITY_MULTIPLE_TASK`：它会强制新建任务，同一个应用按几次就多出几份
  小窗实例。改后目标已有任务时**复用**那份并原地转成小窗（taskId 不变），没有才新建一份

- 入口格不再画单选圈（那读作「这一格是一个可选项」），按点开去哪分两种字形：
  弹一层菜单的（系统导航 / 系统按键 / 媒体控制 / 响铃状态）用 `dots-circle-horizontal`，
  进另一个页面的（「打开应用」）用 `browser-plus`
- 尺寸与配色逐档照 COUI 的 `RadioButton` 抄（24dp；选中 `primary`、未选中 `onSurfaceVariantActions`、

### 「已保存的命令」卡片摘要行的步骤图标

- 摘要行**每一步**行首都补一枚小图标（原来只有引用类步骤那一档有）
- 引用另一条命令（`cmd:<名字>`）的那一步用**被引用那条的真实类型图标**（单条 / 按步数的多条），
  其余步骤用动作图标 —— 与步骤列表同一套 `stepIcon`
- 多条命令的卡片在类型图标右边补上这条命令的**步骤间隔**：它只在多条命令上有意义，
  卡片上原本只有步骤列表、看不到这个参数；文案走 `durationText`（1000ms 以上写成秒）

### 修：单条 / 多条两个 tab 之间编辑态串了

- 换 tab 时把「正在改哪一条」的标记（`editingName`）摘掉：它属于上一个 tab 的那份表单，
  留着会让新 tab 的重名判定把它当成「自己」—— 于是同名不判重、一路覆盖掉另一条命令，
  保存提示也会错报「已修改」
- 表单内容（正文 / 步骤）照旧保留：两套字段互不干扰

### 「命令间隔时长」的下限提到 200ms

- 原来下限是 0（不等待）：`keyevent:` 同毫秒生效，间隔 0 时前一步还没落地、下一步就发出去了，
  两步会挤在一起
- 读配置时也按它钳制，老配置里低于 200ms 的值会被抬到 200

### 「单击延迟」不再跟着「立即触发单击」置灰

- 单击档「按键设置」那张卡里，「单击延迟」滑杆的 `enabled` 不再叠加 `!instantSingle`：「立即触发单击」开着时那一行照常可拖
- 两个状态本来就是两件事 —— 前者管「等多久才判双击」，后者管「双击为无操作时还要不要等」；界面不该替用户把前者锁死
- 判定侧不动：`GestureDetector.onKeyUp` 里「双击为无操作 ⇒ 抬手当场判单击」那条路仍不等双击窗口，行为与之前一致
