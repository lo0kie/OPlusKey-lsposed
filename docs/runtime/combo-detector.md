# 组合判定状态机（`ComboDetector`）

> 这一页是 `app/.../inject/input/ComboDetector.kt` 类头注释的展开版。类头只留一句摘要 + 指向这里；
> 判据的**权威出处**是代码，这一页解释「为什么这么判」，两者不重复、也不互相复述。

## 它是什么、与单键判定器的分工

组合键的判定：**几颗已接管的键**在窗口内先后按下，就当作一次组合，不再各自判单击 / 长按。

判出组合之后执行什么由装配方决定（`onCombo`），这里只回答「哪一档 + 短按还是长按」。

与 `GestureDetector`（单键）的分工：那个判单颗键的手势，这个只判「几颗键的重叠」。一旦认出组合，
立刻把这几颗键的单键状态机摘掉（`resetKey`），否则先按下的那颗会在组合期间判出长按 ——
一次按键执行两个动作。

## 先问 `bindingsFor`

组合成立就会摘掉成员键的单键状态机。没有绑定还照样摘，用户看到的就是「几键同按什么反应都没有」——
这正是最容易被当成「模块坏了」的表现。所以**先判有没有这一档，再动任何状态**：
查不到就把这一下原样交回单键判定器，那几颗键各走各的。

## 顺序按下也算组合（组合的等待压过单键的单击）

判据只是「几颗键的 DOWN 相差不超过窗口」，**不要求同时按着**：先按 A、松手、紧接着按 B
同样算这一档组合。代价面在单键那一侧 —— 参与组合的键按下后要**等满一个窗口**才进单键判定器
（`HeldPresses`），所以「A 的单击」不会在 B 到来之前先跑掉。用户口径：先后按几颗组合键，
只该触发组合，不该每颗各来一次。

**这一整条只服务「等窗口」那一档**（`ComboKey.MODE_WAIT`，默认档）：
按住那两档的成员根本不等窗口，所以也不会被压一拍。

**扫**候选时相对当前这一下算（`now - at <= window`）：几颗键之间夹了一颗不相干的键时，
这一档照样成立。**算不算数**则由这一档自己的**整串跨度**判（`spanFor`）：固定窗口起点开着
就只等一个窗口，关着则按相邻两颗各一个窗口放大（n 颗 = n-1 个）。

**有序无序共用同一套窗口**：`Config.comboWindowsFor` / `comboWindowStartFor` /
`comboHoldWindowStartFor` 只看「这一档自己有没有另设一份」，不看 `ordered`。
档位要不要按配置的先后逐颗落（`ComboKey.ordered`）与「多久之内落完」是两件事 ——
前者影响收不收乱序落下，后者只是时间上限，所以窗口只有一套（v85 起把原来那一组
`combo_ordered_*` 删了）。

## 「先按住某颗」那一档不看窗口，但要真的按住

那两档（`MODE_HOLD_FIRST` / `MODE_HOLD_SECOND`）的判据是「**起点键还按着**」（读 `down`），
不拿时间量间隔 —— 按住三秒再补第二颗照样成立。

起点是谁由这一档**明写**（`ComboKey.starterKey`），不由物理先后推：两颗键几乎同时落下时
谁先上报看硬件，推出来的顺序会摇摆；而按住那一档本来就是「我特意先按这颗」的表态。

反过来有一条下限（`holdMinFor`，每档可设）：起点要按满这么久才算「按住」——
两颗键几乎同时落下（实测相差 0~40ms）不叫按住，那种「一起按」只归窗口那条。
没有这条下限，一起按会按物理先后落进某一种顺序，于是同一个物理动作有时命中、有时整条落空。

上界由长按接管（`longPressPassed`）：那颗键的长按一旦判出来，它已经执行过自己的动作了，
再认组合就是一次按压两个动作。

**「松手时触发」的键没有这条上界**：那一档到点并不执行（动作押在抬手），所以「已经执行过」不成立
—— 按住手势要的正是「按住久一点再补一颗」。凑成之后那颗键的状态机被摘掉，押着的那次长按跟着没。

这条与「只参与非首键的按住组合」（`KeyConfig.comboOnly`）是两件事：那个说的是「这颗键不判单键」，
这个说的是「按住了多久都还算组合的第一颗」。

长按是另一条判据：必须成员**都还按着**（读 `down`）—— 先松开一颗就凑不出「一起按住不放」。

## 两颗走配对，3 颗起走凑齐

- `pairFor`：窗口内挑一颗「配得上、且按下时刻最新」的同伴，两颗成一组 —— 老路径，
  「按下时刻由近到远」只在两颗这一档有意义（三颗以上的候选里挑谁都不是唯一的）。
- `multiFor`：把窗口内按下的那一组**整体**递给绑定闸，「成员多的赢」由 `Config.comboFor`
  判（`maxByOrNull { keys.size }`）。成员表按**命中那一档自己的清单**取，候选里夹的别的键
  不算成员（它们还得自己走单键判定）。

界面现在能造三颗（`ComboKey.MAX_KEYS`），四颗以上仍只对手改配置生效 —— 判定、执行、
日志三处都是同一条真链路，不是旁路。判定侧这一层的判据全部**按成员集算**、不认「两颗 / 三颗」
这种数字：多成员那条从 3 颗起（`MULTI_MIN_KEYS`），「等更宽的一档」按**真子集**判，
整串跨度按成员的颗数放大 —— 四颗、五颗走的是同一条路。

## 组合进行中再来的按键只出一组

组合进行中再来的按键整条吞掉（按下 + 抬手），所以「几颗里有两组组合」也只出**先凑成的那一组**。

**唯一的例外是「更大的一档被这一下凑齐了」**（`absorb`）：子集那一档总是先成立，
不让位的话更大的一档永远轮不到 —— 那一档换成更大的、抬手时派发的是它，仍然只出一组。

**另一条例外**是「这一组只在等更宽的一档、而成员已经松过手」（`absorb`）：那一组先收尾派发，
这一颗走正常判定 —— 否则「刚按完 A + B，紧接着单独按 A」会整颗失灵到窗口结束。

## 更宽的一档还来得及 ⇒ 先不派发

【{A,B} 与 {A,B,C} 同时配着，且 {A,B,C} 的窗口被调宽】小的一凑齐就派发，等于大那一档永远
只剩「所有手指同时落」才成立 —— 用户把大那一档的等待时间拉长，手感上却一点没变（先松手的
那颗已经把小的那一档的动作用掉了）。所以凑成之后先问一句「还有更宽的一档吗」：

- 有，且**它整串的跨度还没用完**（从最早那一颗算，`spanFor`）⇒ `awaitWider`
  记下这一档、把派发压到那个时刻；
- 期间来了它缺的那颗 ⇒ `absorb` 换成更大的一档（换过去之后接着等更宽的那一档，
  于是 `{A,B}` ⊂ `{A,B,C}` ⊂ `{A,B,C,D}` 能一级一级往上走）；
- 到点还没凑成 ⇒ 才派发小那一档（`awaitWider` 里那一枪）；
- 期间成员还都按着 ⇒ 来的按键照老规矩吞掉；**已经松过手** ⇒ 这一组是「待派发」状态，
  先派发它、再让新按下的那颗走正常判定（`absorb`）。

等多久只按更宽那一档算，**与这一档自己的窗口无关**：等的是「下一颗还来不来得及」，
而不是「这几颗算不算同时按」。

有一条**不**跟着等：长按。这一档按住超过自己的阈值就照旧派发（`scheduleLong`），
之后也不再升级 —— 长按本身就是「按住不放」的明确表态，到那一刻就不该再等下一颗。

## 长按阈值取组合自己的

`ComboKey.longPressMs` 是这一档自己的（默认 350ms，与单键默认值同档）。不用某颗成员键的阈值：
两颗键可能各配一个值，取谁的都是任选其一；而「一起按住多久算长按」是这一档的语义。

**按顺序触发的组合没有长按这一档**（`ComboKey.hasLong` = `!ordered`，等待与按住都一样）：
这一按的语义就是那串先后本身，再叠一档「按住不放」等于给同一串动作配第二个结果。
判定侧于是不排长按枪（`scheduleLong` 第一句就返回），界面也不摆那一页。

## 成员连击与组合长按：后者优先

按住档里那颗**唯一成员**键还有一整套连击（单击 / 双击 / 三击 / **单击后长按**），它的判定器
（`memberChain`）是复用 `GestureDetector` 的第二个实例。它与组合长按有一处**重合手势**：

> 首键按着 + 成员键按住不放 —— 既是「组合长按」，也是成员的「单击后长按」（第一击点一下、
> 第二击按住那一支）。

两者只能出一个结果，判据收在 `ComboKey.longActionExists`（本组 `long` 或任一场景块的 `long`）：

- **长按这一档有动作** ⇒ 这一按归组合。连击链的「单击后长按」让位（不派发、不收尾），
  且组合长按一判出就把连击链这一轮清掉（`yieldMemberChainOf`）。理由有两条：同一次按压不该
  出两个动作；连击链判出**任何**一档都会 `finishCombo`，而它会把「长按连续触发」那串定时链
  一起撤掉 —— 第一枪排在间隔之后，于是一次按住永远只有一下（真机症状：
  「按住组合的长按连续触发无效」）。
- **长按这一档无操作** ⇒ 连击链照旧全权处理：那一下没有别的落点，「单击后长按」就是用户配的
  那一档。

单击 / 双击 / 三击**不在让位之列**：它们是抬手才判的短按，与长按不重叠，照旧归连击链
（判出一档就把组合收尾，这是「一次按压一个结果」的老语义）。

## 线程模型

与 `GestureDetector` 同一条输入线程（DOWN/UP 都在它上面进来），长按那一枪走 `handler`
（main looper）。跨线程的字段一律 `@Volatile`。

## 显式阶段（`Combo.phase`）

一组组合在判定侧走四个阶段，由 `Combo.phase`（`ComboPhase`）派生、是**唯一**的分派入口：

- `PAIRED`：已凑成、长按枪还挂着，还没等到长按阈值；
- `AWAIT_WIDER`：还有更宽的一档来得及 ⇒ 先不派发，等它窗口结束（`waiting != null`）；
- `LONG_FIRED`：长按已判出，但没在连发；
- `REPEATING`：长按判出后 `longRepeat` 那串连发还在跑。

阶段由 `waiting` / `longFired` / `repeatShot` 三个标志**派生**，不另存一份可变状态（避免两头漂）。
判「这一组现在处在哪个阶段、该走哪条路」只看 `phase`；判「某个事实有没有发生」（长按判出没有）
仍直接读 `longFired` —— 两者分工不同：前者是分派、后者是查事实。

「回到空闲」收口在 `finishCombo(c)`：撤枪（`cancelShots`）+ 清 `combo` 两件事**成对**，
六处「收尾」只有一个入口，不会只撤一半让定时链到点再补派一次。

`StarterKeepPending` 是**游离于 `combo` 生命周期之外**的一笔账（组合已收尾、首键还按着时欠的
一次长按补派），它是一个独立的小状态，与上面四个阶段并排、不混进 `phase`。

## 可选功能的装配（`DetectorBinds`）

首键补派、按住档固定窗口起点、四格窗口这三样是**可选功能**，早先写成类体里的 `@Volatile var`
+ `apply { }` 再设（构造参数清单已贴 detekt 上限），那样「必须设」被降成可空、装配有两个入口。
现在收进 `DetectorBinds`，构造时一次给全、类型非空。
