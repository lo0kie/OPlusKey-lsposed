# 按键是怎么变成手势的

## 一、接管方式与两级开关
原版 `OPlusKey` 的按键接管是「独占输入设备 + uinput 转发」：

```
/dev/input/event*  →  daemon 独占 grab  →  自己判定单击/双击/长按
                                        →  uinput 转发不拦截的事件
```

这条路能做，但有三个天生的问题：

1. **需要 root daemon**，还要一层 supervisor 看护循环（`service.sh`）保证它不被杀；
2. **独占设备会漏事件**：触摸屏如果声明了 `KEY_POWER` 也被 grab 掉，`EV_ABS` 收不到，触摸就失灵 ——
   daemon 里得专门写一条「跳过触摸设备」的规则；
3. **要维护一套 C 代码 + NDK 交叉编译**。

本版换的那条路：

```
system_server 收到按键
  →  ColorOS 专为侧键写的策略类 StrategyActionButtonKeyLaunchApp 被调用
     （系统设置 → 侧键 背后的实现）
     →  我们 hook 这个方法
        →  启用了 → 记按下/抬起 → 判定手势 → 执行动作
```

接管点是**按候选表逐层降级**挑出来的（`bridge/Framework.kt`）：

```
1. StrategyActionButtonKeyLaunchApp      ← ColorOS 专为侧键写的策略类，首选
2. PhoneWindowManagerExtImpl             ← OPPO/一加对 PhoneWindowManager 的扩展
3. PhoneWindowManager                    ← AOSP 兜底 interceptKeyBeforeQueueing
```

因此：

- 不需要 root（模块跑在 system_server 里，本来就是 system uid）；
- 不需要 uinput，不碰 `/dev/input`，不会影响触摸；
- 不需要 C 代码与 NDK。

代价是**崩溃范围从「输入法起不来」变成「整个系统起不来」**（开机循环），所以注入侧的纪律（AGENTS.md 五之二）比原版严格得多。

### 只管内置的侧键（自定义键另算）

`KeyId` 的**内置**清单只有 `PLUS` 一个分量。原版把电源键与音量键也做成内置键，本版不这么排：

- 电源键要保系统电源菜单与紧急呼叫；
- 音量键要保组合键（上下同按 = 截屏）与长按连调。

但**用户可以自己收集**自定义键（最多 `KeyId.MAX_CUSTOM_KEYS` = 3 颗），音量±与电源在可选范围内
（用户口径）。收下之后那几颗键归模块管、没收集时照常放行给系统；它们注入的那一下仍由
`KeyId.INJECTABLE_CODES` 认出来放行，所以不会形成自持循环 —— 不许收的是
`KeyId.RESERVED_CODES`（主屏幕 / 返回 / 媒体 / 截图 / 通知中心 / 最近任务 / 静音）。

### 两道开关：模块总闸 与 每颗键

接管与否是**两级相与**，判定侧只有一个入口（`inject/ConfigChannel.enabledOf`）：

| 层级         | 字段                   | 界面入口                                   | 关掉的后果                                             |
| ------------ | ---------------------- | ------------------------------------------ | ------------------------------------------------------ |
| **模块总闸** | `GlobalConfig.enabled` | 首页「启用按键绑定」那一行                 | 一颗键都不接管，页面整片灰，常驻提示「按键绑定已关闭」 |
| **这一颗键** | `KeyConfig.enabled`    | 「按键绑定」页 ⋮ 菜单「停用 / 启用这颗键」 | 只这一颗不接管，模块与其它键照常                       |

- 总闸**打开之前**要过免责声明（`Config.disclaimerAccepted`），弹窗只在首页（`HomeDisclaimers`），
  确认后由 `acceptDisclaimerAndEnable` 一次写完「记录 + 总闸」；
- 逐键那一行**每颗键都有**（侧键也有），一步到位、不弹确认 —— 它不丢数据，菜单里一字之差就能改回来；
- 停用的键在菜单清单里名字后面挂一枚 `pointer-cancel` 图标（`MenuEntry.Row.stateIcon`，走 COUI 的
  `hint` 槽，那一槽只有 40dp，所以只能是图标不能是文字）；
- **老配置的迁移**：拆开之前「总闸」就是 `keys.plus.enabled` 那一位。`ConfigDto` 读到没有
  `global.enabled` 的文件时，把总闸取那一位的值、把侧键这一颗写成「开着」——
  否则升级后用户打开总闸会看到「开了没反应」（侧键还是关的）；
- 导出 / 导入：只把总闸写成关、每颗键一律写成开（`ConfigBundle.withShareableKeys`）。

侧键 keyCode 只在 `core/model/KeyId` 里定义：`KeyId.keyCode` = 735（`KEYCODE_ACTION_BUTTON_CLICK`，Linux 侧是
`BTN_TRIGGER_HAPPY32`），另有一份白名单 `KeyId.acceptedKeyCodes`（=
`{735, 780, 781, 782}`，含 ColorOS 策略类路径的内部注入码，781 的补齐记录见 `../device/side-key.md` §14.4）。

第一层 `StrategyActionButtonKeyLaunchApp` 确实存在，落在 `oplus-services.jar`，入口是外层
`actionInterceptKeyBeforeQueueing` —— **只挂外层**：内部回调 `$2`
是它的纯转发（`../device/side-key.md` §14.2），挂它只会让同一次按键被回调两次（2026-10-13 起 `Framework.kt` 不再挂），

（`ActionButtonProvider` + SQLite）。**完整的类名 / 方法签名 / URI / 表结构记录在
[`docs/device/side-key.md`](../device/side-key.md)** —— 改 Hook 面之前先读它，不要再靠猜。

## 二、按键是怎么变成手势的

daemon 的判定是 `poll()`
驱动：它自己收原始事件，超时醒来就知道「这段时间没有新事件」，所以能直接判「长按到点了」「双击窗口过了」。

LSPosed 这边拿到的只是「framework 调了一次侧键策略方法」，所以判定必须**改成定时器驱动**（`inject/input/GestureDetector.kt`）：

```
按下 → 起一个「长按计时器」(longPressMs)
     同时清掉双击窗口

长按计时器先到 → 判长按，抬手不再触发
抬手 → 起一个「双击窗口计时器」(doubleClickMs)
窗口内又来一次按下 → 判双击
窗口到了还没有第二次 → 判单击
```

定时器全跑在 system_server 的 `Handler` 上，**回调里绝不阻塞**
（一次按键处理必须立刻返回，否则整个系统的按键都会变卡）。

**时间基准一律 `elapsedRealtime()`；熄屏排双击窗口时持一段唤醒锁把 CPU 顶住。**
`uptimeMillis()` 在深度睡眠里不走，而抬手之后设备会立刻睡：双击窗口那一枪（`postDelayed`）不到点，
窗口的截止时刻却还停在「刚刚」—— 下一次按下（真实过了几秒）会被判成双击，前一下的单击则永远不派发
（真机：熄屏按一下没反应，4.6 秒后按第二下却判成双击）。所以所有窗口与比较都走 `elapsedRealtime()`；
并且 `PowerManager.isInteractive` 为假时，排窗那一步先要一段**带超时**的 `PARTIAL_WAKE_LOCK`
（窗口 + 500ms 余量，不计引用数、不主动放），让窗口那一枪在 uptime 上真走到点。

- **代价**：熄屏单击要晚一个双击窗口（`doubleClickMs`）才执行。曾经是「熄屏抬手当场判单击」，
  熄屏即时响应但双击整档作废（熄屏下每一下都是单击）—— 双击不能没有，改走顶醒 CPU。
- 取不到 `PowerManager` 时静默降级回「熄屏判不出双击」，按键本身不受影响；判定侧不为了顶醒 CPU
  把异常抛回输入线程。
- 唤醒锁由装配方注入（`KeyHooks.holdAwake` 借 `SystemContext` 取服务），判定器不碰 Context。

### 「松手执行额外动作」（长按之后松手那一刻的第二个动作）

长按那一档可以再挂**一个独立的动作**（`KeyConfig.longRelease`，由开关 `longReleaseOn` 管着）：
按住到长按时长先执行长按动作（照旧），松手那一刻再执行这一个 —— 两个事件分开、各自执行、各配各的。

```
长按计时器到点 → 派发 long（LongPress，照旧，可连发）
抬手（这一按已判成长按）→ 若 releaseBound（开关开 + 已挑动作），再派发一条 release
```

- `release` 是一档**触发条件**（`GestureTrigger.Release`，id 就是 `release`），不是第四档手势：
  它不参与连击链、也不进条件分支（松手那一格归块自己，见 `pickReleaseAction`），执行侧由 `KeyConfig.actionOf(Release)`
  直接取 `longRelease`。
- **开关与动作是两位**（`longReleaseOn` / `longRelease`）：开着但还没挑动作是合法状态 —— 松手
  什么都不做。合成一位（「有动作 = 开」）的话，用户在开关上点一下就会立刻执行一个他没挑过的动作。
  两处都只认 `KeyConfig.releaseBound`（= 开关开 && 动作非 none && 没开「松手才触发」）。
- **谁接管这一按，谁自己的开关说了算**（`pickReleaseAction`）：块命中长按时执行的是**那一块**
  的松手格 —— 块自己那一格没开就是「这一下什么都不做」，**不回落**按键那一格；一块都不中才看
  按键的 `longReleaseOn`。两边的开关都必须一起看：只看「存下来的动作」，挑过动作之后再关开关
  照样会执行（用户口径「这一档没开额外动作，按下去却冒出来一个」）。
- 与「长按连续触发」**不冲突**：一个管按住期间重复几次，一个管抬手时再做一件 —— 两者可以
  同时开着（按住期间照常连发，松手补这一条）。判定侧对此不需要额外判据，`longRepeats` 只把
  「松手才触发」排除在外。
- 没配额外动作时这条广播根本不发 —— 行为与这一位出现之前逐字一致。
- 组合键那一档**还没有**这一项：判定侧只发「哪一档、短按还是长按」，没有松手那条通道，
  所以组合那张卡上不画这一行（摆一个拨了没反应的开关比没有更糟）。

### 「松手才触发」（长按的时序：到点即触发 / 等抬手才触发）

长按本来是**一到阈值就执行**。`KeyConfig.longFireOnRelease` 换成另一种时序：到点只把这一按
**标成长按**，动作等**抬手那一刻**才执行一次。

```
长按计时器到点 → 只置 longPressFired（不派发、不排连发）
抬手（这一按已判成长按）→ longFireOnRelease ⇒ 派发 long 一次
```

- **两种时序只能占一种**：到点即触发（默认）/ 松手才触发（本条）。「松手执行额外动作」
  （上一节）与这一条互斥 —— 两条都要用「松手那一下」，同时开着就是同一刻执行两个动作。
  互斥收在数据层两位属性里，判定侧与界面都只读它们：`longRepeats` 把 `longFireOnRelease`
  排掉（到点没执行过就没有可重复的起点），`releaseBound` 本身也被 `longFireOnRelease` 排掉。
  **「松手执行额外动作」不再连坐连续触发**：它只与这一条互斥，按住期间的连发照旧。
- 只**置状态位、不派发**是关键：计时器那一枪要是不置 `longPressFired`，抬手会把它当短按再补一次
  单击 —— 一次按压执行两个动作。抬手收尾统一走 `GestureDetector.finishLong`，三种时序在那儿分开。
- **UP 丢了怎么办**：这一档把唯一一次执行押在抬手事件上，UP 一丢就等于「这颗键坏了」。所以到点
  之后再排一枪 `RELEASE_FALLBACK_MS`（15s）：还按着就按 UP 已丢处理 —— 就地执行一次，并在
  `Pending.closedWithoutUp` 上把这一次按压**封掉**；那个迟到的 UP 走 `finishLong` 时只清状态，
  不会执行第二次。谁先到谁负责（两侧都在 `synchronized(p)` 里判，先到的赢）。
- **执行侧免检过期**：`release` 走到 `GestureExec.handle` 的过期闸时传 `keepLate = true` ——
  积压的按下可以丢（丢的是「再来一下」），丢一条松手却是「整次按压零响应」。去重那半照旧
  （转发侧的补发 `sent_at` 相同，仍会被挡掉）。
- 拨这一位**不清** `longReleaseOn` / `longRelease`：额外动作让位但值留着，关掉这一位之后原样回来
  —— 切换时序不该顺手把用户挑过的动作扔掉。
- 界面：这一行排在长按那一档的**最上面**（它管「什么时候执行」，下面两族管「执行几次 / 松手还
  做不做别的」）；开着时「松手执行额外动作」与「长按连续触发」都**置灰不隐藏**，灰着点一下会说明原因
  （`DisabledHint`）。
- 置灰**分两层**（`LongPressSpec.enabled` / `repeatBlockedReason`）：整页级的原因（主开关关 /
  链路没通 / 配置只读）灰整张卡；「这一档的长按动作**自己**不支持连发」（多条命令 / 灵感语音）
  只灰「连续触发」那一族（开关 + 振动 + 间隔），**不连坐**时序两行与长按延迟 —— 那三项跟连不连发
  没有关系。真机上撞到过：长按=开始灵感语音、松手=结束灵感语音，整张卡全灰，刚配好的松手那一行
  点都点不了。
- 组合键那一档同样没有这一项（`LongPressSpec.releaseSupported = false`），那一页整行不画。

### 三击 / 四击（第 3 击起的档位）

三档之外还有**连击次数更多**的档位（`click3` / `click4` …，配置里落在 `KeyConfig.extraClicks`）：
它们不是新的判定方式，只是把连击链**多走几格**。

```
第 1 击抬手 → 开一个窗口（doubleClickMs）
窗口内又按下 → 链上的击数 +1；没到这颗键配的最高档就继续等下一击
数到最高档 → 那一击抬手时派发 Click(n)；窗口到了还没凑齐 → 派发已经数到的那个击数
```

- **最高档由 `clicksForJudge` 说**（= 这颗键真的绑了动作的最高击数，随配置广播到注入侧）；
  判定器不读动作表，它只数到第几下。执行侧按 `KeyConfig.actionOf(trigger)` 取那一档的动作。
- **单击的代价按最高档算**：配了三击，单击最坏要等**两个**窗口才派发（`KeyGesturePlan.waitFor`）；
  四击就是三个。这是判定本身的性质，不是顺手能消掉的延迟 —— 想快就别把高档绑上。
- **场景块也认这几档**：一块场景存的是「档位 → 动作」那张表（`SceneRule.actions`，键是
  `GestureTrigger`），所以单击 / 双击 / 长按 / 三击 / 四击都能被同一块场景接管 ——
  「只给三击配了场景、直接绑定那一格空着」是合法配置，判定侧照样会为它把连击链走到第 3 下
  （`Config.boundClicks` 把场景里配过的最高击数也算进去）。组合键的场景块只有短按 / 长按两档
  （`ComboKey` 没有双击与多击）。
- **界面入口**：「按键绑定」页的第 4、5 页（三击 / 四击），与前三档同一张动作网格、同一条写盘
  路径（`KeyConfig.withAction`），所以界面配出来的与手改 / 导入配置的是同一份数据。
- **这两档要自己在「独立设置」页顶部分别打开**（`KeyConfig.extraClicksOn`，一颗键一份、逐档一位）。
  没开的档：界面不排那一页、场景块不列它、判定不数到那儿（`clicksForJudge` 只算开着的）、
  执行恒 `None` —— 单击也就不必为它多等窗口。**逐档而不是一个总开关**：开三击让单击多等一个窗，
  开四击还要让三击也等，只要三击的人不该被迫接受四击那一份延迟。**不跟随「使用独立设置」那颗
  总闸**：那一族是「公共设置这一项可以另设一份」，而公共设置里没有「多击」这一项。关掉再打开，
  `extraClicks` 那张表原样回来（关的时候不清表）。老配置升级按「表里有没有东西」倒推
  （`KeyDto.clicksOn`；v39 那个布尔也照样认）。

## 二之三、单击后长按（两段式）

`GestureTrigger.ClickThenLong`（配置里 `click_then_long_on` / `click_then_long`）——
**第 1 击抬手之后，第 2 击在连击窗口内按下并按住**超过长按阈值。它和双击互斥：
同一颗键的第 2 击，快速抬起是双击、按住不放是这一档。

- **它不延长连击链**：判定仍只数到第 2 击，`clicksForJudge` 不受影响，单击的等待窗口
  与这一档出现之前完全一样。这也是它不能并进 `extraClicksOn` 的原因 —— 多击延长的是
  链长，这一档只是在第 2 击按下时顺手排一枪长按（`GestureDetector.onKeyDownLocked`）。
- **开关**：`KeyConfig.clickThenLongOn`，默认 `false`。关着时判定侧根本不在第 2 击上排枪，
  所以不会把一次快速双击误判成长按。
- **与长按的区别**：松手时**不走**长按那一档的收尾（「松手执行额外动作」/「松手才触发」
  都只属于「第 1 击按住」那条路），`finishLong` 里按 `p.clicks >= 2` 让位。
- **与三击共存**：第 2 击按住、此时链上还会继续数第 3 击 —— 到点时若已数到第 3 击，
  那一枪作废（判据 `clicks <= 2`），三击链照常。
- **它有一套自己的参数**（与长按那一族**同名不同槽**，调这一档不动普通长按）：
  `click_then_long_press_ms`（第二段按多久算数）/ `_repeat`（按住期间连续触发）/
  `_repeat_interval_ms`（间隔）/ `_repeat_vibrate`（每次都振动）/ `_release_on` + `_release`
  （松手再执行一个动作，判定侧发 `GestureTrigger.ClickThenLongRelease`）。
  「松手才触发」那一行**不摆**：这一档本来就是按住之后松手才结束。
- 界面：与三击 / 四击一样，要自己在「独立设置」页顶部打开才出现那一页；那一页再单独设上面那几项。
- **双击是无操作、而「忽视无操作多击手势」开着时，两下轻点各算一次单击**：这一档让判定侧不能在第一击
  抬手就收线（要在第 2 击上等长按），于是那两下本来会被判成 `Click(2)` —— 而双击没人要，用户看到的是
  「按两下什么都没发生」。现在第 2 击**抬手**那一刻连发两条 `Click(1)`
  （判据 `KeyConfig.doubleFallsBackToSingles`：开着「忽视无操作」+ 后面没有连击要等 + 双击没绑动作）。
  配了三击 / 四击、或**场景里**给双击配了动作时**不拆**：第 2 击是连击链上的一格，拆开就把那条链废掉
  —— 所以广播里那个「最高绑定击数」发的是**没抬过下限**的数（宿主 `Config.judgeLimit`），
  下限由两边各自加一次。两条同类手势的 `sent_at` 由转发侧保证严格递增
  （`GestureForwarder.nextSentAt`），否则宿主会把第二条当「补发」吞掉，用户看到的是「只执行了一下」。

## 二之四、执行时提示：一句话模板（`$key` / `$gesture` / `$action`）

弹什么由 `GlobalConfig.toastTemplate` 这一句决定，拼装在 `ToastNotice.render`（`:core`）。
三个占位符：

```
$key      键名（内置键走字典，自定义键是用户起的名字）
$gesture  手势（单击 / 双击 / 长按 / 三击 …）
$action   动作名（自定义命令是命令名）
```

- **默认模板就是拆分之前那句话**（`侧键 - 单击 → 手电筒`，见 `ToastNotice.DEFAULT_TEMPLATE`）：
  老配置没有这一项时字段表补的就是它，升级前后弹出的字一模一样。
- 替换是**单趟扫描**：替进去的值里再出现 `$action` 这种字样不会被二次展开（用户就把自己那颗键
  起名叫 `$action`，也不该把动作名填进去）。
- 空模板 = 用默认那句；拼完是空白时也退回默认那句 —— 弹一条空 Toast 等于「按了没反应」。
- 这一项**只有落盘那一列**（`ConfigFields.F_TOAST_TEMPLATE`，与 `F_TOAST_ON_RUN` 同档）：
  提示由宿主执行器在 `host/GestureExec.noticeIfNeeded` 里弹，注入侧不读、也不弹。
- 键名与手势是**分两段**传进 `noticeIfNeeded` 的（`triggerParts` / `comboParts`）：模板要能只用其中
  一段，先拼成一句再拆回来做不到。日志那边仍拼成「侧键 - 单击」，读的是同一对值。
- 界面那一行（`首页 › 按键设置 › 按键行为`）只在「执行时提示」开着时出现；**清空即恢复默认**，
  所以它同时也是「改回去」的入口。行首是 `align-left` 那颗（与开关那行的气泡分开）。
- 编辑窗（`NameDialog`）里两处提示分工：输入框的**占位**只写「留空则用默认」（不把默认那句抄进去 ——
  那句随时会变，摆进占位就是一处会过期的说明），框下面那行**常驻小字**写三个占位符各是什么。
  按钮区还多一颗**重置**（`DialogButtonRow.onReset`）：按下就**把默认那句写进配置并关窗**，与按「确定」
  一样是一次落盘，只是值取默认 —— 不去填输入框，省得有人以为「重置」只是把框里的字换掉。
  那两句带 `$` 的文案不给源码兜底 —— 兜底审计按字面量逐字比，而 Kotlin 里必须写 `\$`
  （见 `GeneralScreen` 里那条注释）。

## 三、「交还系统」为什么不提供（2026-10-14 删除）

模块曾经有一档动作叫**「交还系统」**（`native` / `passthrough`）：选了它，按下去就不拦这个键、让系统那套照常跑。
**这一档已经整条删掉**，因为它要的语义在原理上做不到，而且失败方式很难看。

**做不到的原因：判定手势必须先把 DOWN 吞掉。**

侧键的单击 / 双击 / 长按是**我们自己在拦截点里数出来的**（见第二节：DOWN 之后排计时器、UP 之后排双击窗口）。也就是说：只要还想让双击 / 长按这两档生效，DOWN 就必须被吃掉。而「交还」要的是**这一次按键原样给系统**
——两者不可能同时成立：

- 真放行（`return false`，原事件给系统）⇒ 这次按压整键都归系统，**双击 / 长按上绑的命令一起失效**；
- 吞下来再补一次注入（旧实现）⇒ 补出去的是**合成事件**（`deviceId = -1`），ROM 那侧不一定认它，用户看到的是「按下去没反应」，而且它会再次触发框架那条
  `what=1` 场景派发。

用户报的现象正是这两条各占一半：**「交还系统无效，且直接拉回模块页」**——无效来自合成事件不被认，拉回模块页来自那条被放行的场景派发（框架给宿主的那条的效果是「宿主打开设置页」，而那一页被我们替换掉了）。

**为什么不保留「整键交还」这一档：** 它只能表达「这把键我不要了」，而那正是**主开关**的语义（`KeyConfig.enabled = false`
⇒ 拦截路径整条不生效、行为与原生完全一致，见第一节）。再留一档动作表达同一件事，只会让人以为「可以只交还单击」，然后在双击 / 长按上踩空。

**删除范围**（不留兼容，配置格式还没发布）：

- 动作类型 `Action.Native` / `Action.Passthrough`，以及网格里那一格（`ActionCatalog`）；
- 判定侧的放行回调（`GestureDetector.onPassthrough` → `GestureForwarder` 的 `PHASE_PASSTHROUGH` 广播）；
- 宿主侧的「重注入一次按键」（`KeyInjector.injectForForward`）与自持循环兜底闸（`GestureReceiver`）；
- 宿主侧「放行时把场景派发放过去」那一整套**配额 + 扣留补投**机器（`SideKeyGestureHooks`）——
  它服务的是「动作档判为放行」，那一档已经没了。现在那条派发按另一条更简单的判据走
  （`host/PressTrace`：这一下**有没有被模块认领**；见本节末与 `../device/key-codes.md` 二十八之末）。

**副作用（也是修好的两件事）：**

- 那条 `what=1` 场景派发不再按「动作档」有条件放行 ⇒ 模块接管的按压不会再莫名其妙把设置页拉起来；
- 单击那档的默认值从 `native` 变成 `none`（无操作）。想「回到原生」用主开关，不要用动作档。

**停用的键（`KeyConfig.enabled = false`）仍然要原生动作**：注入侧对它原样放行，ROM 那条 `what=1`
就是它原生动作的载体，所以宿主侧不能一律吞 —— 判据是「这一下有没有被模块认领」
（认领经广播到达，`host/PressTrace` 记时间戳；窗口内认领过就吞，否则放行）。这条与「动作档放行」
不是一回事：前者是「这颗键不归模块」，后者要的是「同一颗键的某一次按压归系统」。
