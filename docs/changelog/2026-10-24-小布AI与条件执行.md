## 小布 AI：四件能力收拢 + 小布助手

### 加：小布助手（`oplus:voice_assist`）

- 与系统「长按电源键唤醒小布」是同一个能力：同一个语音服务、同一套 extra。
- 起法照 ROM：`PhoneWindowManagerExtImpl.startSpeech` 是拿 **system_server 自己的身份**去
  `startForegroundService`，目标 `com.heytap.speechassist.core.SpeechService`，带
  `caller_package=android` 与 `start_type=512`（语音助手自己表里的 `power_key` 那一档）。
  宿主未必有那个签名级权限，所以这一档**不在宿主起**：`ActionRunner` 的 `oplus:` 分派里单独
  分出一支，转给注入侧（`StatusBarBridge` 新增 `voice_assist` 指令），在 system_server 里起。
- 包名运行期挑：`com.heytap.speechassist` → `com.oppo.speechassist`（新旧两代），都没有就只记日志。
- 需要 `system` 作用域（与电源菜单 / 通知中心同一条通道）。锁屏那一支（`FloatSpeechActivity`）
  没做 —— system_server 里借来的 Context 起界面必失败，宁可少一支也不假装支持。
- `start_type` **不能照框架指令里那个 `1024` 抄**：那是 `MSG_POWER_LONG_PRESS_FOR_SPEECH` 的消息号。
  真机逐个值验过 —— `1024` 只有 FGS 起来、界面不出来；`512` 界面直接到前台。
- 取证、配方原文与这次核对的完整过程见 `docs/device-findings.md` 第三十节。

## 条件执行页：两颗常驻 FAB + 检查挪到点击

### 改：落盘点收成右下角叠着的两颗常驻 FAB

- 原来是「右下角一颗 FAB（添加）+ 底部一条磨砂工具条（重置 / 确定）」，两个落盘点一个在角上、
  一个在底边中间。现在收成**右下角两颗一叠、都常驻**：上面「添加」、下面「确认」，间距 12dp。
- 两颗**都不跟滚动显隐、也不按状态出现 / 消失**：它们是这一页并行的两个入口，忽隐忽现比
  「按下去被告知差什么」更难理解。检查统一放在**点确认那一刻**（见 `BranchSaveFab`）。
- 内容底部留白按「两颗都在」给死（`FAB_STACK_BOTTOM_CLEARANCE`），滚到底时表尾注脚停在按钮上面。
- 随之下线：这一页底部的磨砂工具条（`BranchActions`）。**「重置」也一起没了** —— 它原先只在那条
  工具条上，作用是把草稿丢回配置；返回时那道「放弃改动？」确认窗是同一件事的另一个入口。
  「什么都没改」时点确认直接退页，不白写一遍同样的表。
- 新组件：`ui/PageFab.kt` 的 `PageCornerFabStack`（右下角一叠，位置与间距一处收口）+
  `FAB_STACK_GAP` / `FAB_STACK_BOTTOM_CLEARANCE`。

### 加：确认时只拦「下面挂着死分支」

- 分叉是「从上往下、第一条成立的赢」。按顺序往下扫，某一档的取值在**第 i 条**凑齐 ⇒ 第 i+1 条
  起永远不会被执行。所以要报的只有一种情形：**凑齐那一刻后面还有规则**。
- 早先的判据是「表里某档取值全在就报」，把两种合法情形也一起拦了：两个完全对立的条条件正好收尾
  （最后一条就是那一档的另一半）、以及只是「这两个条件本身」。现在都不报。
- 判据只有一处 `deadFrom`（`branchSaturatedReason` 与下面的行内标记共用同一次扫描）：
  命中就提示「当前条件恒成立，后面的条件不会执行」，这一次不落盘。添加那颗不拦。
- 同一颗按钮上还有另外两条检查：半成品（空条件 / 空动作）照旧拦；**什么都没改**则直接退页，
  不白写一遍同样的表。
- 「前台应用」不参与（候选是包名，永远凑不齐）；取值空着的、`isUsable` 为 false 的条件也不计入。

### 加：死分支在条件那一行末尾标红

- 哪一条永远不会执行，不必等点「确认」被拦下才知道：条件那一行行尾先标一句红的
  「不会执行」（新键 `command.branch_dead`，用 `colorScheme.error`）。
- 为什么不在小标题上：`SmallTitle` 只能给一整串字，染不了一半（`·` 分隔符也就没处上色）。
- 「哪几行标死」与「保存会不会被拦」共用同一次扫描（`deadFrom` → `deadIndexesOf` /
  `branchSaturatedReason`）：一处改了另一处不会各说各的。

### 改：条件菜单的置灰放宽到「这一档的取值全用过了」

- 原来是「这一档用过一次就整档灰掉」：加过「屏幕状态 - 亮屏」之后，「屏幕状态 - 锁屏」也一起灰了，
  用户只能回去把已有那条改掉 —— 而这是两条不同的条件。
- 现在一级按「**有没有没用过的取值**」判：屏幕 / 充电 / 耳机 / 媒体 / WiFi / 响铃 / 方向这几档，
  只有候选**全部**用过才置灰；「前台应用」照旧永不因此置灰（可多条，只要应用不同）。
- 重复挡在**二级**：已经存在的那一个取值单独灰掉，点一下说「这个取值已经加过了」
  （`command.branch_duplicate_value`）。一级那条提示仍管「整档都加满了」。
- 判定的最小单位从「条件种类」换成「条件种类 + 取值」（`UsedCondition`，取值走
  `effectiveValue`，老配置没有取值的那几条按默认档算）。

### 改：条件页返回时的确认窗说「条件」，不说「命令」

- 「离开这一页、放弃未保存的改动」那道窗原先借的是命令页的文案（「放弃未保存的命令」），
  这一页草稿里明明是条件表。`LeaveDiscardDialog` 现在把标题交给调用页：
  条件页给「放弃未保存的条件」（`dialog.discard_condition_title`），命令页照旧。

### 禁用态不许用 `Modifier.alpha` 压暗

中途给「按不动」的确认套过 `Modifier.alpha(0.4f)`，真机反馈**阴影被裁成正方形**：
alpha 会把这颗按钮单独合成一层，层的边界就是按钮方框，库内部那层
`graphicsLayer(shadowElevation)` 画的阴影落进层里就被裁掉了。后来禁用态改配色 ——
最终连禁用态也撤了（检查挪进点击），这条教训留着：**要压暗先想清楚层的边界**。

### 改：空态的键名加一对括号，表尾注脚只留一句

- 空态那句「将执行按键绑定里的 …」里，键名要**看得出是一颗键**。按键名套过一个**描边圆角方框**
  （键帽）：为了画那个框，`Feedback` 得加一个 `textContent` 插槽、空态得按 `%s` 把一句话拆成
  三段、还得管中英词序 —— 换来的是**一句话断成几截**，读起来像三行注脚。
- 定稿（用户口径：「不要圈起来啊，就加两个符号就行」）：**只加一对括号**，整句回到一个 `String`：
  `将执行按键绑定里的「侧键」- 单击`。`textContent` 插槽、`KeycapLabel`、那几个间距常量一起删掉 ——
  为两个符号养一套排版不划算。
- 括号用**对角方括号**「」，与停用提示「「侧键」已停用，可在菜单里启用它」同一对 —— 同一个东西
  在两处一个长相；英文那边用弯引号 `“”`（正是英文停用提示里那一对），按 `I18n.effectiveLanguage` 分。
- 表尾注脚只留「以上都不成立时，执行按键绑定里的命令」，去掉后面那截「：侧键 - 单击」——
  这一档是哪一颗键、哪一档手势，顶栏的尾随小标题已经写着。

- 内容区停用后压到 `DISABLED_ALPHA`（0.4），而大标题右边那行「快捷键」还是满亮度，
  读起来像那一区仍然是活的。
- `PageHeader` 新增 `subtitleColor`（透给库的 `trailingSubtitleColor`），停用那支把
  `onSurfaceVariantSummary` 的 alpha **乘** `SUBTITLE_DIM_FACTOR`（0.5）。
- **第一版不生效，原因值得记**：写成了 `copy(alpha = 0.5f)`。这个 token 在 coui 里是
  `Color(0x66000000)`（alpha 0.4），`copy(alpha = 0.5f)` 等于把它从 0.4 **抬**到 0.5 ——

## 修：两种「按不动」的提示，一条来回刷、一条只有一条

现象：「设置项已停用，可在菜单里启用它」这条，连点几下会**一条条往上刷**（旧的被挤下去、
新的重新入场）；而「还有条件没选完」不管点几下，永远只有一条在原地改字。

- 根因在提示队列的**语义位**（`HintQueue` 的 `slot`）：给了位，同一个位的提示是「这条改字」；
  没给位，每次点击都是**新的一条**（新 id ⇒ 重新播入场 ⇒ 上一条被顶掉）。
- 「还有条件没选完」早就有位（`HINT_SLOT_COMMAND`）；禁用提示那一支走的是
  `LocalDisabledClick` / `PageMenuPopup` 两处 `hint(...)`，两处都**没给位**。
- 现在共用 `HINT_SLOT_DISABLED`：点同一个按不动的开关，是那一条在改字；换一个开关，还是同一条
  （位相同）—— 与「还有条件没选完」的表现一致。

## 底层：一块可以带**多条**条件（先不做 UI 入口）

用户口径：「把组合条件的底层接口做出来，一个块允许加多个条件，先不做 UI 入口」。
所以这一版只动**模型 / 线格式 / 判定 / 校验**，界面上仍然是「一行一条条件」。

### 模型：`StateRule.conditions` 是一个列表，「且」由判定层负责

- `StateRule(gesture, condition: BranchCondition?, action)` → `StateRule(gesture, conditions: List<BranchCondition>, action)`。
- 判定 `appliesTo` 改成 **逐条都要成立**（`conditions.all`）：一条不成立就不再问后面几条（短路），
  所以配了三条条件的块在第一关就挡掉时，不会再去读另外两个系统开关。
- **空表仍然「永不成立」**：那是「还没选条件」的半成品，不能因为「一条都没有」就当成恒成立。
- 关掉「`copy(condition = …)` 这种写法」：它会把同一块里其余几条悄悄抹掉。留了三个有名字的动作 ——
  `replacingCondition(at, c)`（换第几条，其余留着）、`addingCondition(c)`（末尾再添一条）、
  `withoutCondition(at)`（去掉第几条），外加 `single(gesture, condition, action)` 这个单条件构造。
- 只读的 `condition` 还在，等于 `conditions.firstOrNull()`：那批「一次只编辑一条」的界面调用点
  （挑应用、条件菜单、行内文案）不用改语义。
- 两个新判据：
  · `isReady` = 至少一条且每条都 `isUsable` —— 保存前那句「还有条件没选完」改用它，
  一块带几条都算同一个问题；
  · `isContradictory` = 同一档给了两个不同取值（亮屏 + 锁屏）—— 这块**永远不成立**，
  与「配完了」是两件事。**还没有界面提示**（要新增字典键），先备着。

### 线格式：加一格 `conditions`，老那一格继续写

- `StateRuleDto` 多一格 `conditions: List<String>`；读的时候优先看它，空了才回落到老的 `condition`。
- 写的时候：**只有一条**仍写老那一格（`condition`），**全量**也写进 `conditions` ——
  版本 11 之前的读方读到的还是原来那条，不会把用户一堆规则读丢。
- 多条时 `condition` 留空：老读方看到「条件认不出」会整条丢掉 —— 那是它能给出的最好结果
  （它没有「且」，硬塞第一条会变成「命中一条就执行」，比丢掉更糟）。
- 一块里**只要有一条**条件认不出，**整块丢掉**：留着其余几条等于把「且」悄悄放宽成「有几条算几条」。
- `ConfigCodec.VERSION` 10 → 11（本轮加了字段，见那一段的纪律）。老文件照旧能读（`version < VERSION`
  不校验 md5），下一次写盘自动升到 11。

### 校验与显示：都按「整块」算

- **死分支扫描**（`BranchDeadEnds`）：一块的**任意一条**条件所属的档在前面已凑齐 ⇒ 这一行永远轮不到
  （前面那条只要求这一档就已经赢了，其余几条成不成立不影响结论）。但**记账只算单条件的行** ——
  多条件的行赢了不等于「这一档每个取值都有人接」，让它记账会把后面误判成死的。
  顺带把「从哪一条开始死」的定义改准：现在返回的是**第一条永远轮不到的行**，标红范围 `from..last`。
- **重复 / 置灰**（`UsedCondition`）：一块里几条条件都算「用过」，否则用户能把同一条在别处再加一遍。
- **挑应用去重**：扫全部条件，不只是第一条。
- **行内文案**：几条条件用「 + 」连（语言中性，不必新增字典键）；行首图标取**第一条可用的条件**。
- **挑应用回来点亮哪一行**：取的是「前台应用」那一条，不是第一条 —— 手改的配置里应用条件排在第二
  位时，原来那一页会一行都不亮。
- **写回**：挑应用改的是「前台应用」那个槽位，条件菜单改的是第 0 条；两者都**只动那一个槽位**，
  不再整组替换（那一版的多条件入口一上来就会误伤手改的配置）。

### 执行侧：一次按下里，同一个条件只判一次

`GestureExec` 里那个 `matches` 回调加了一层**局部** `HashMap` 缓存。判据里有反射与小窗那张表，
而一张规则表里好几块都会要求「亮屏」—— 一块带三条条件之后这个浪费会翻倍。缓存只活在这一下里，
跨次缓存会让「切到微信再按」仍按上一次的应用走（那正是注释里写死不许做的事）。

### 这一版**没做**的

- 界面上「再添一条条件」的按钮 / 条件列表的第二行 —— 一处都没加，仍然是一行一条；
- 同档互斥（`isContradictory`）的提示文案；
- 「一块里几条条件」的行内排版（现在是一条 `A + B` 的文字，没有分行与独立编辑）。

## 修：死分支判断「没了」，同时把组合条件的判定做细

用户报「条件执行的死分支判断怎么没了」。根因是上一轮**我自己改出来的回归**。

### 回归：判的是「这一行自己的档凑齐了没有」

上一轮把 `deadFrom` 从「带 `continue` 的循环」改写成 `firstOrNull` 时，判据被写成了：

```kotlin
// 错的：只看这一行自己那几条条件所属的档
val dead = kinds.any { kind -> kind.choices.all { it in seen[kind] } }
```

于是 `[亮屏, 锁屏, 充电中]` 里第三行（充电）被判成**没死** —— 充电那一档当然没凑齐，
可屏幕那两条已经把每一下都接走了。正确的判据只有一句：**前面只要有一档凑齐，这一行及后面全部
轮不到**，与这一行自己要求什么无关。现在用 `saturated: MutableSet<ConditionKind>` 记「已经凑齐的
档」，每行开头先看它非空否。

顺带把「从哪一条开始死」的定义钉死：`deadEndOf` 返回的是**第一条永远轮不到的行**，
标红范围 `from..lastIndex`，与点「确认」时那句拦截共用一个结论。

### 加：组合条件的**集合包含**判定（`SUBSUMED`）

光有「某一档凑齐」抓不到组合条件这种情形：`[亮屏]` 在前、`[亮屏 + 微信]` 在后 —— 屏幕那一档没凑齐
（只写了亮屏），但**只要后者成立，前者必定也成立，而它在前**，所以后者永远轮不到。

判据因此加了一条：前面某一行的**条件集合 ⊆** 这一行的条件集合 ⇒ 这一行永远轮不到（原样重复一条
也落在这里）。两条都成立时先报「凑齐」——它说明的是整张表到头了，比「这一条被盖住」
更根本。

- 记账仍然**只算单条件的行**：多条件的行要求别的也成立，它赢了不等于这一档每个取值都有人接；
  但多条件的行**被判死**没这个问题（前面凑齐了，它必然轮不到）。
- 没条件 / 取值没配完 / 档认不出的行不参与包含比较：那样的行本来就不该成立，拿它比包含只会得出假结论。

### 文案：只说结论，不讲机制

新加的那句本来写成「前面已经有一条更宽的条件，这一条永远轮不到」（用户口径：**文案不用写细节**）。
现在两种原因各自一句短的：`当前条件恒成立，后面的条件不会执行` / `有一条条件不会执行` ——
**哪一行**不会执行，行上那枚「条件 N · 不会执行」已经写着，句子不必再复述一遍判据。

规模上：死分支扫描从 `BranchDeadEnds.kt` 改名为 `BranchDeadCause.kt`（文件里多了一个 `BranchDeadCause`
枚举，detekt 的 `MatchingDeclarationName` 要求文件名与那唯一的顶层声明同名）。
