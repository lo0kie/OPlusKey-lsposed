### 首页提示的影子被切：根因是库的视窗，修在 item 里

- 现象：首页那条常驻提示的胶囊，**顶上那道影子被齐平整切**（真机截图能看见一条直边）
- 量出来的根因：COUI 的 `SnackbarHost` 是「内容多高就多高」的 `LazyColumn`（内部 `reverseLayout` + `contentPadding`
  底部 28dp），**item 外面那层盒子就是裁切边界**；库给胶囊的内边距是
  `padding(horizontal = 16.dp, vertical = 4.dp)`，于是影子的可见范围 = 胶囊 ∓ (16dp, 4dp)，而胶囊那圈是
  `Shadow(elevation = 26.dp, offset = (0, 4.dp))` ⇒ **往上要 ~22dp，只有 4dp 有地方**
- 真机取样（1272×2772 / density 560）：顶上切在胶囊上方 **4dp**（灰阶一步跳 10）、左右切在
  **16.0dp**（三点独立采样都精确落在 `x = 229`，灰阶 0→3）；底下有 4+28 = 32dp 所以没事
- 试过「给 `SnackbarHost` 加
  `padding(bottom = 16.dp)`」——**没用**：那是从视窗往里抠，切痕跟着胶囊一起上移（这也正是用户说的「和 padding 没关系」）
- 正解：走 `SnackbarHost` 的 `content` 槽位，把胶囊包进一个 `padding(SNACKBAR_SHADOW_ROOM)` 的
  `Box`，裁切边界跟着 item 一起撑出去；`SNACKBAR_BOTTOM_INSET` 删掉（那一档本来就该补在 item 里）
- 页面根 `Box` 上的 `.clipToBounds()`
  **不是**元凶（`fillMaxSize`，底边就是屏幕底边，切不出这条线），继续留着裁转场出画；取证手法与全部实测数据见
  `docs/device-findings.md` 十八

### 触觉反馈挪回宿主侧：振 = 服务真的在跑（推翻本节前面那一次搬家）

- 用户 2026-10-14：「整体服务没起来时按键不要振动，不要会误以为功能能用」。判定侧（system_server） **振不出这个保证**
  —— 它判出手势就振，可手势转给宿主之后宿主在不在、能不能执行，它并不知道（只发广播），于是会出现「振了一下，但什么都没发生」；用户读到的就是「功能好着呢」
- 位置：回到宿主侧，且落在 `host/GestureReceiver.runAction` 的**动作即将执行那一刻** （`r.run(action, …)`
  前一行）。宿主进程没起来 / 模块没注入进宿主 ⇒ 这个方法根本走不到 ⇒ 不振。走到它就意味着：宿主在跑 + 主开关开着 + 不是放行 + 不是无操作 + 不是连续触发的重复 —— 正是「整体服务在跑」
- 判据一条没变，全在宿主侧现读的配置上：`global.vibrate` 开着、`action !is Action.None`、`!repeat`； `native` /
  `passthrough` 在 `handle` 里就返回了，走不到这里。时长仍是 30ms oneshot
- 注入侧整条撤掉：`GestureDetector` 的 `haptic` / `hapticsEnabled`、`SideKeyInterceptor` 的 `haptic` 参数与
  `hapticsEnabled` 写入、`KeyHooks` 的 `HAPTIC_MS` 与那段借 `Vibrator` 的 lambda； `GestureReceiver.appContext`
  从「留着没人用」回到真的在用（当初它的注释就写着「振动反馈要用它取 Vibrator」）
- 时序代价（明知而取）：比「按下那刻就振」晚一趟广播 —— 宿主常驻时几毫秒、感知不到；宿主刚被拉起时要等那 300ms 的补发，但那时**动作**也是 300ms 才发生，**振与动作仍然同时**（这才是要的语义）
- 执行侧动的是 `host/`（不是注入侧），`kill`
  宿主主进程即可生效；但**注入侧那份旧代码要等整机重启才会停**，重启前会「注入侧旧的一下 + 宿主新的一下」振两次 —— 重启后只剩一次
- **真机验过（不是静态推断）**：直接 `am broadcast`
  一条假手势进宿主（**绕开注入侧**，所以那一下不可能是旧代码振的），日志与振动台两份证据咬得上：
  ```
  15:26:45.861 (host) 侧键·单击 → shell:true（宿主进程执行）              ← runAction 跑了
  15:26:45.863 (vibrator) com.oplus.gesture (uid=10277) 63ms usage=TOUCH  ← 晚 2ms，就是新加的那一下
  ```
  再把 `global.vibrate` 改成 false：执行数 3→4（动作照跑），宿主振动条数**停在 4 不变**
  ⇒ 开关这一路也是通的（测试把「单击」临时换成无副作用的 `shell:true`，测完已按备份原样还原，临时文件已清）
- ⚠️ **顺带挖出一个更要紧的问题**（不是本次改动引入的）：用户那次「按了没反应」是手势被宿主当**过期包丢掉**了 ——
  `sentAt` 在判出手势那一刻就打好了，可真正 `sendBroadcast` 那一步挂在 **system_server 主 looper**
  上，实测卡了 2.89s，宿主按 `STALE_MS = 2000` 丢掉。**这一路现在也不会再振了**（丢弃发生在 [runAction]
  之前），但**动作本身还是会丢**。判据、完整时间线与待办见 `docs/device-findings.md`
  十九；修法（把转发挪出主 looper）属注入侧改动、要整机重启，**待用户点头再做**

### 配置读不懂时不许写回：页面进只读

- 起因：2026-10-14 真机上「振动反馈」自己变成了 `false`。查下来**不是页面写的** ——两份模块日志里都没有
  `设置页写入：vibrate=0`；是**外部改动了那个文件** （root 非原子写会先截断，而宿主**每条按键前都读一遍**这个文件）
- 根因在**读的那一侧只有两态**：`ConfigStore.read()` 把「读不到」与「读不懂」都退化成
  `Config.DEFAULT`，而默认值长这样 —— 主开关**关**、三个手势全是「无操作」、**不振动**。页面拿这份默认值渲染，用户随便改一项（那次是
  `long → zoom:mini`）就**把整份默认值写回了文件**，等于把用户的配置整份抹掉。这次只丢了一个「振动」开关（一眼能看出来），再往后一次就是三个绑定一起丢
- 改：读拆成**三态**（`ConfigStore.Load`：`Ok` / `Absent` / `Unreadable`），并在 `ConfigCodec`
  里把「读懂了但字段缺失」（走字段默认值，老文件兼容）与「压根读不懂」（`parseOrNull` 返回 null）分开
  - `Absent`（首装 / 还没写过）⇒ 用默认值，**允许写回**
  - `Unreadable`（文件在、但读不了 / 读不懂）⇒ 页面进**只读**：`write()` 一律拒 + 弹「配置读取失败，未保存」
  - 只读态的出口：**重进页面**（`createView`
    重读一次）、⋮ 菜单的「默认界面」，或「重置配置」——那是用户明说要丢掉重来，`resetAll`
    先清只读位再写（有意为之的例外，注释里写了）
- 界面：首页那条常驻提示多一种文案
  `CONFIG_READ_FAILED_HINT`「配置读取失败，请重进页面」，与「模块不可用，正在等待系统响应」分开 —— 这一种**要用户动手**，说「等待」会把人引到错方向；整页总闸跟着加
  `!configReadOnly`；「运行状态」里「设置生效」优先报「配置读取失败」，而不是把「宿主读到默认值」说成「主开关已关闭」（那会让人以为是自己关的）
- 只读方（宿主侧每条按键 / 每次执行 / 报活）仍走 `ConfigStore.read()`
  的「退化成默认值」：对它们这是对的（读不到就按不接管处理，行为与原生一致），**写方必须走 `load()`**
- 只读态下的**置灰范围**（2026-10-14 用户补的要求）：主开关**也**跟着灰（`linkReady && !configReadOnly`），⋮ 菜单里**只留「默认界面」与「关于模块」**（`rowsEnabled = linkReady && !configReadOnly`）
  - 为什么必须补：真机上一进页链路还没报到（`linkReady=false`）⇒ 主开关是灰的；等注入侧回包一到、`linkReady`
    变 true，它就**自己重新亮起来**了，用户当场拨了三下（日志里三次 `拒绝写回：plus_enabled=1`
    —— 写被拒了，但**「拨了没反应」比「一开始就灰着」更难读**）

### 修「按一下变成收起的小窗」：落点几何取错了档

- 现象（真机）：`zoom:mini` 按下去，前台应用变成**右上角那条最小化窗**，不是展开的普通小窗

  就等于把「展开」的动画落到了收起的位置
- 修法：展开档改用**展开档**的标准几何，新增常量 `EXPANDED_BOUNDS` / `EXPANDED_SCALE`，不再调
  `getMiniFlexibleTaskInfo`（这两个常数的**最终取值**见下一条 —— 本条这一版取的还是屏幕矩形，是错的）
- 两个来源此前在 `docs/zoom-window.md` §7.4 与 `docs/device-findings.md` 附六里被**混记成同一个**
  （「`getMiniFlexibleTaskInfo` 的真机标准值 ≈ 展开档几何」）—— 两边都已订正并写明订正原因
- 这组落点常数与机型允许表绑定（PLK110 / 1272×2772 @560dpi），加机型要连同它重测，注释里已写明
- ⏭️ 属注入侧改动，**待整机重启验证**落点

### 修「小窗对了、但比原生小一圈」：喂给 `setRememberPosInfo` 的必须是**配置矩形**

上一条重启验完之后，真机第二轮才暴露出来的：小窗**不再是收起档**了、位置也对，但比 ColorOS 原生的小一圈，用户一眼判「还是不对」。

- 取证（两条路各取一个数，不靠肉眼、不靠猜）：

  | 来源                                                      | 结果                                                         |
  | --------------------------------------------------------- | ------------------------------------------------------------ |
  | 我的截图（逐列扫亮像素，脚本落在 `.temp/measure_win.py`） | `(126,319)-(942,1770)` = **817 × 1452**，宽占比 **0.6423**   |
  | 用户手调出的正确形态（同一支脚本）                        | `(126,319)-(1145,2130)` = **1020 × 1812**，宽占比 **0.8019** |
  | 正确形态的 `dumpsys activity activities` → `Task.mBounds` | `Rect(126,319-1398,2580)` = **1272 × 2261**                  |
  - 两个尺寸的比值**两轴都一样**：`1020/817 = 1812/1452 = 1.2485 = 1/0.8017` —— 不是巧合
  - 左上角两版**都是 `(126,319)`**，所以「位置没错、只有尺寸错」

- 根因：`setRememberPosInfo(Rect, float)` 的 `Rect` 是**应用配置矩形**，系统会把它的尺寸 **再乘一次 `scale`**
  才是屏幕上的大小：

  ```
  屏幕尺寸 = Rect.size × scale
  ```

  上一版把**屏幕矩形** `Rect(126,319-1146,2131)`（1020×1812）直接喂了进去 ⇒ 又被缩一次 ⇒ `1020 × 0.8017 = 817`（高度
  `1812 × 0.8017 = 1452`）—— 与实测逐位吻合。而 `Rect.left/top` 是**直接照搬屏幕坐标**、不含缩放，所以左上角一直是对的

- 修法：`EXPANDED_BOUNDS` 改为 **`Rect(126,319-1398,2580)`**（1272 × 2261），另立 `EXPANDED_SCREEN_BOUNDS`
  记录**屏幕口径**（1020 × 1812）供验收比对；日志改成一条印全「配置矩形 → 乘 scale → 屏幕落点」，下一轮一眼可核
- 顺带得到一条定论：**小窗的逻辑尺寸恒为 `1272 × 2261`、两档共用**，屏幕上多大只由 scale 决定 ——收起档交叉验证
  `542 ÷ 0.2397 = 2261`（展开档 `1812 ÷ 0.8017 = 2260.4`），同一个数
- ⚠️ 由此暴露出**两个小窗 API 的 `Rect` 语义是反的**：`getMiniFlexibleTaskInfo` 返回**屏幕矩形**、 `setRememberPosInfo`
  收**配置矩形**，一进一出正好差一个 scale —— 这是这一轮最容易踩的地方，已连同取证数据写进 `docs/device-findings.md`
  **附七**，`docs/zoom-window.md` §五表头与 §7.4 也加了警告
- ⏭️ 属注入侧改动，**待整机重启验证**

### 小窗验收：只报能看到的事实，不再宣称档位

- 起因：上一轮补的三态验收（展开 / 收起 / 不是小窗）**给了假绿灯**
  —— 它打出「已是**展开档**小窗（宽占比 0.8019）」，而屏幕上实际只有 `817` 宽。用户看到的「还是不对」就是这么被放过去的
- 根因：它读的是 `OplusAppInfo.appBounds`，那是**配置矩形**；两档小窗同为 `1272 × 2261`，
  **读出来一样**，本来就分不出档位 —— 上一版把「配置宽占比」误当成了「屏幕宽占比」
- 改法：`taskZoomWidthRatio` → `taskZoomConfigRatio`，语义与注释一并改准；分界常量 `COLLAPSED_MAX_WIDTH_RATIO(0.5)` →
  `ZOOM_CONFIG_WIDTH_MIN_RATIO(0.95)` ——它现在验的是「预置几何有没有被 system_server 吃住」（正常 ≈
  `1.0`；上面那个「小一圈」的 bug 会读到 `0.80`），**不是**档位
- 三处口径全部改成**只报事实**（是不是小窗、几何吃住没有），档位一律注明「以截图为准」： `putForegroundInMiniWindow`
  的验收、`verifyMiniOrFallback`、`putInCollapsedMini`
- 降级链不变：几何没吃住 ⇒ 退 recents 正门重收一次；走完一轮不再循环重试

### 落点几何改由宿主侧下发：调几何不再需要整机重启

- 起因：用户一句「你为什么不直接在系统里试一遍呢，每次都要重启」—— 这是真问题，而且是**设计造成的**，不是机制逼的
- 机制那半：LSPosed 只在**进程启动那一刻**注入模块 dex，`system_server`
  是长驻进程 ⇒ 注入侧的代码改动必须整机重启才加载；宿主侧（`com.oplus.gesture`）只要 `kill` 掉进程就生效
- 设计那半：落点几何本来**写死在注入侧**，而它恰恰是要反复试的参数 ——于是变成「一次重启换一个仍然错的结果」（上一轮就是：重启一次，拿到的还是那个小了 0.8017 倍的窗口）
- 改法：几何**随小窗指令的 extra 下发**，注入侧那份降级为「宿主没带」时的兜底：
  - 宿主侧 `AppLauncher.EXPANDED_CONFIG_BOUNDS` / `EXPANDED_SCALE` = **要调就改这里的真值**
  - `FlexibleWindowBridge.send(…, bounds, scale)` 带 extra；注入侧 `readBounds()` 读，缺项则走兜底
  - 传 4 个 int + 1 个 float，不传 `Rect`：跨进程传 Parcelable 要管类加载器，广播这条路上多一事不如少一事
  - 注入侧日志加「（宿主下发 / 注入侧兜底默认）」标注 —— 一眼看得出宿主是不是旧版
- ⚠️ 这一次仍需整机重启（注入侧**协议本身**变了：要新增读 extra 的代码）；但这是**几何调参的最后一次重启**，之后改
  `EXPANDED_CONFIG_BOUNDS` = `kill` 宿主进程 = 几秒钟
- 写进 `docs/zoom-window.md`
  **§十一「调参放哪边：改哪边就得重启谁」**，附一张试错成本对照表；并注明 §7.5 那袋 bundle 参数（`MaxScale` / `MinScale`
  / `SupportRatios` / `CaptionName`） **若也要反复调，照同一模式挪到宿主侧**

### 伪造态开出来的小窗是**半成品**：改用 recents 正门

几何修对、重启验完之后暴露的：**几何全对，但窗口不能用**。用户原话「点击被视为拖动，也没有菜单和操作条和圆角」。真机逐条坐实：

  **窗口集合完全同构**，都没多出操作条窗口 ⇒ 操作条不是独立窗口、是挂在应用窗口内部的，顺着「找不到操作条窗口」这条路找不到东西
- 顺带发现一处文档错记：`dumpsys activity activities` 里 ActivityRecord 的 `windowType` 在展开档 / 伪造态 /
  **连桌面**上都是 `2` —— 它和 §五表里那个 `OplusZoomWindowInfo.windowType` **是两个同名字段**，不能拿来判档位（已在
  `device-findings.md` 附八写明）
- 根因（推断，四条同一指向）：**框架的「柔性任务注册」那一步没做**。操作条视图 / 圆角 / 拖拽与输入都配在那一步，而伪造态只捅了三个状态字段 +

- ⚠️ **本次改动全在宿主侧** ⇒ `kill` 掉 `com.oplus.gesture` 即生效，**不需要整机重启**

### 查清「前台 → 小窗」为什么没过渡：壳子是**过渡**装的（2026-10-14，未改代码）

上一节把「伪造态是半成品」的根因推成了「柔性任务注册那步没做」。这一轮逐行比 `logcat`
之后**修正**：壳子（圆角 + 操作条）是那条**窗口过渡**装的，所以更可能只是「过渡 abort 的后果」。

**三组对照**（详见 `docs/device-findings.md` 附九）：

|                      | 目标任务               | 多出来的一步                                   | 过渡结果                            |
| -------------------- | ---------------------- | ---------------------------------------------- | ----------------------------------- |
| 桌面「近期任务浮窗」 | 在最近任务里（非前台） | **`skipCurrentOrAdjustChange … launchFrom=2`** | leash → `MultiSpringAnimation` ✅   |
| 模块 recents 正门    | 普通全屏、前台可见     | 无                                             | `No transition roots … so abort` ❌ |

- **`zoomLaunchFlags=2` 两边一样** ⇒ 变量是**调用方身份**，不是参数
- 壳子的归属从日志直接认出来了：`adjustSurfaceForTransitionIfNeed(cornerRadius=91)` 与
  `finishTransition will update task's caption visible` 都只在真过渡里跑
- **前台任务确实没有过渡 root**，清干净状态复测仍然 abort —— 与附二一致，不是脏状态造成的
- 顺带：桌面那个入口菜单项叫「**近期任务浮窗**」。按「小窗」在桌面 dex 里**一条都搜不到**，我一开始搜错了词，白绕一圈
- 顺带：`LaunchSourceType` / `determineLaunchSourceType` / `isLaunchSourceType` 在 **`services.jar` 的
  `classes4.dex`**（不在前两个 dex）

**两条待试的路**（都还没做，都要注入侧改动 + 一次整机重启）：

|       | 做法                                                                                                                                                            | 赌注                                                                                              |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |

### 加 debug 通道：注入侧的实验不再需要整机重启（新增能力）

- 起因：本工程最贵的成本是**注入侧的迭代速度** —— 注入侧跑在 `system_server`
  / 桌面进程里，LSPosed 只在**进程启动那一刻**注入 dex，所以注入侧改一行就要整机重启，一轮几分钟。小窗「小一圈」那个坑就是这么一次次重启试出来的。用户要求加一条通道，并**固化成 debug 通道**
  （长期保留，不当临时件）
- 新增 `inject/system/ProbeChannel.kt`，四个 op：
  - `dump` —— 列出某类的声明方法/字段**连参数类型**（专治「签名靠猜」，本工程踩过多次）
  - `call` —— 反射调一个方法并打返回值/异常（`target=static|service`，`args` 按形参类型转换）
  - `state` —— 只读打任务状态（bounds、`TaskExt` 那几个字段、操作条视图建出来没有）
  - `corner` —— 给任务窗口 surface 设圆角（`SurfaceControl.Transaction`）
- **两个落点**：`system_server`（复用 AMS 广播入口的 hook）+ **桌面进程**（`KeyModule.onPackageReady` 新增
  `LAUNCHER_PACKAGE` 分支）。桌面那个落点是「调用方 pid == 桌面进程 pid」那条路的前提
- **三条安全边界**（缺一条都不能上）：
  1. `DEBUG_PROBE` 编译期常量 —— release 里这些代码连同调用点一起被 R8 折掉，**不是运行时判断**
  2. 来源校验单列一条 `KeyHooks.isFromRootOrSystem`（只放行 root / system）——它的发送方本来就不是宿主，跟 `isFromHost`
     那条不能共用；普通 App（uid ≥ 10000）仍进不来
  3. 每个 op 整体包 catch（调用点在 AMS 广播入口，漏异常出去就是开机循环）
- 落地时踩到的两处**隐藏 API**（都只能反射）：`android.app.ActivityThread`（直接 import 编译不过）、
  `SurfaceControl.Transaction#setCornerRadius`（`SurfaceControl` 类本身在公开 SDK 里，这个方法不在）
- 新增 `docs/debug-channel.md`：用途、安全边界、两个落点与作用域要求、四个 op 的完整 adb 用法
- 顺带澄清一处**包名广播路由**：带 `-p` 时 `system_server`
  的 hook 照样会看到那条广播（它拦的是 AMS 入口），所以一次广播可能打两份日志，按进程标签 `(system)` /
  `(com.android.launcher)` 分辨

**为什么这条通道是「两个一起来（A + C）」的最佳载体**：A（从桌面进程发起）和 C（自己补壳）都是 **运行时实验**
—— 有了这条通道，发现签名、试调用、在桌面进程里发起全部走广播， **不用为新想法再编译、再重启**。

⏭️ **待做两件**：① 在 LSPosed 里把 `com.android.launcher` 加进本模块作用域；② 一次整机重启。之后 A /
C 的验证都在运行时进行。

### 小窗原生缩小动画：**已成立**（2026-10-14 真机，用户亲眼确认）

接着上一条。两轮真机把三道坎逐个定死，最终**动画可见且可用**
—— 全屏应用向屏幕中心缩成小窗，而且是**框架自己的动画器**在跑（不是手搓）：

- **每帧守卫 `isFlexibleTaskAndHasCaption(task)`** ⇒ 「先动画后转换」**结构上不成立** （普通全屏任务每帧
  `updateAnimationLayer task is not flexible task` 直接 bail，spring 空转）。顺序**只能**是「先真转换、再播动画」。
- **`startFlexibleTaskToMiniAnimations` 开头有 `isInTransition` 过滤** ⇒ 转换后立刻调会被**静默剔掉** （只有一句
  `current task is in transition`，看不出是失败）。改用同族的
  `startFlexibleSpringAnimation`（**无这道过滤**）⇒ 转换后立刻启动，不必等过渡收完。
- **`endAnimation(205)` 那道闸无害**：`createSpringAnimation` 只创建不 `.start()`，所以 `isAnimRunning()`
  恒为 false，`cancelSpringToMiniAnimation` 早返回。
- 诊断实验（`MINI_ANIM_START_SCALE` 临时 `0.2f`）证明**每帧 transform 真的作用在画面那层 surface 上**
  （窗口从左上角冒出再移到中间）⇒ 不需要自建 leash。
- **取证教训**：验动画别用「录像启动后 sleep N 秒再触发」推算时间点 —— `screenrecord`
  启动延迟会让抠帧窗口整个错开，看起来像「画面没动」。**锚点用画面里的状态栏时钟**，与 logcat 的动画时间对齐。

### 小窗验收改成「窗口有没有落在屏幕内」（2026-10-14，宿主侧）

### 浮层菜单的关闭动画（2026-10-15）

### 「命令列表」两处过渡修（2026-10-15）

**一、删掉最后一步时「添加命令」行会「移过头再拉回」**

- 现象（真机逐帧量底边）：1 步 → 0 步时卡片底边从 `1970` 一路收到 `1759`， **又弹回 `1766`** —— 收过头 7px 再弹回来。
- 根因：库的 `CardListPosition` 会给**圆角边**各加一份 `HeadOrTailPadding`（2dp），且行的**最小高度同步抬高** ⇒
  `Full`（上下都圆角）比
  `Tail`（只有下边圆角）高 4dp。而「添加命令」行的位置原来按**展示层行数**算（`cardListPositionOf(display.size, display.size + 1)`）—— 退场行在动画期间仍留在
  `display` 里，这一行就停在 `Tail`，**等退场动画播完、那行被摘除**才翻成 `Full`，高度当场 +4dp。那一跳就是「拉回」。
- 修法：位置改按**数据**（`draft.steps.isEmpty()`）算 ⇒ 翻档发生在过渡**开始**那一帧，与行高动画同时进行、看不出来。复验：底边单调收敛到
  `1766` 并停住，**结束回弹消失** （起始多一帧 +7px，下一帧即被收缩盖过）。
- 同处那条分隔线的判据由 `steps.isNotEmpty()` 改成
  `display.isNotEmpty()`：退场行还在占位时线要陪着它走完，否则行才刚开始缩、线先没了。

**二、「已保存的命令」从有到无原来没有过渡**

- 原来是 `if (saved.isEmpty()) … else …` 硬切：删掉最后一条时整片网格「啪」地消失、空状态「啪」地出现。
- 改成 `AnimatedContent`（180ms 淡入淡出 + `SizeTransform` 同长收放）。
  - ⚠️ 目标态传的是**列表本身**，不是 `saved.isEmpty()` 那个布尔：`AnimatedContent` 把
    **旧值**交给退场那一侧，只传布尔的话退场侧拿到「非空」分支却已无数据可渲染，那半场会瞬间塌成 0 高、过渡等于没有。
  - `contentKey = { it.isEmpty() }` ⇒ 改某条命令（内容变了、空非空没变）不重播过渡。
  - ⚠️ 这个 compose 版本里**没有 `using` 中缀**（实测 `Unresolved reference`），尺寸动画走
    `ContentTransform(targetContentEnter, initialContentExit, sizeTransform)` 显式给。
- 真机复验：删掉最后一条时卡片淡出、空状态淡入，容器高度同步收。

> ⚠️ 顺带记一笔：`CardListPosition`
> **会改行高**这件事对别处同样成立 ——任何「按展示层行数算卡片位置」的列表，只要行数在动画期间会变，都会吃到同一跳。
