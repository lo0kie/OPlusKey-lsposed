### 模块不可用的原因精确到「用户该做什么」

- 首页那条常驻提示原先把「链路没齐」一律报成「模块暂不可用，请稍候」，现在拆成可分辨的九档：
  机型不适配 / 系统版本等待适配 / 配置读取失败 / 按键绑定已关闭 / 后台服务未运行 /
  模块未生效（作用域漏 system、或装完从未重启）/ 模块已更新，重启后生效 / 系统接口不匹配 / 设置未同步
- 「换包后没重启」从「没回音」里拆出来：注入侧回包带上 `ModuleInfo.BUILD_ID`，
  页面比到不是本包 ⇒ 只说这一件（重启手机），不必再让人去 LSPosed 里翻作用域
- 「模块没启用」这一档不判、也不写：页面能画出来就说明模块已加载（页面本身就是模块的代码，
  跑在宿主 `:ui` 进程里），真没启用时用户看到的是宿主原版页面
- 判据收进 `blockedReason()` 一处，首页提示与「选动作被拦住」的 toast 共用 —— 原先两处各写一份 `when`
- 主开关那一档改用独立文案「按键绑定已关闭」：它原来借的是 `status.disabled`（字典里是「模块未启用」），
  用户会去 LSPosed 里找一个根本没关的开关

### 格式化与静态检查配置收到根脚本：一处定义，两个模块共用

### 构建提速三件：闸与包分家 / 配置缓存 / `build_id` 改任务产物

起因是这台机器上「跑一次检查」很卡。查下来**不是 CPU 弱**（16 核 32 线程），是内存：
32 GB 里只剩 3 GB 空闲 —— 游戏客户端占 6.2 GB，五个 java 进程（**两个** Gradle 守护 +
一个 Kotlin 守护，各自 `-Xmx4096m`）占 5.2 GB，系统 `Memory Compression` 已经在 5.1 GB 上
拼命换页。于是「构建慢」的主因是换页，不是计算。

能改的三处：

**(1) 三道闸与打包分家 —— 新增 `./gradlew gate`**

- 过去的口令是 `spotlessCheck detekt lintDebug assembleDebug assembleRelease assembleBeta` 一把梭，
  其中 `assemble*` 会带上**两遍 R8**（release 与 beta 各一遍；`beta` 虽然 `initWith(release)`，
  两个变体产物独立、压缩与资源收缩各跑一次）
- 实测两个量级：`spotlessApply detekt compileDebugKotlin` 13~27 秒；全量 + 三个包 2 分 18 秒 ~ 2 分 28 秒
- `gate` 是根脚本注册的聚合任务（`:app`/`:core` 各自的 `spotlessCheck` `detekt` `lintDebug`），
  路径**写死**而不是 `findByName`：后者找不到就静默跳过，那道闸会在不知不觉中不再被跑，而它看起来仍是绿的
- 顺带把 CI 的检查步骤换成 `./gradlew gate`（同一条命令，省一处漂移）

**(2) 打开配置缓存**

- `org.gradle.configuration-cache=true`。实测 `./gradlew gate` 第二次起 **41 秒 → 3 秒**
- 前提是「配置阶段不许有只在这 一次成立的取值」，这条以前**不成立**（见 (3)）
- 不设 `configuration-cache.problems=warn`：那条会把「缓存不可用」降级成警告，于是某天它悄悄退回
  普通构建、性能白丢而 CI 仍然绿。与本仓其它闸同一条纪律 —— 该响的就让它响

**(3) `build_id` 从 `resValue` 改成任务产物**

- 原实现 `resValue("string", "build_id", SimpleDateFormat(...).format(现在))` 取的是**配置期**时钟
- 两层后果，第二层要命：
  · 配置期干执行期的活（跑一次 `./gradlew help` 也在算日期）；
  · 开了配置缓存后配置阶段整个被跳过 ⇒ 那个值被一起复用 ⇒ **一天里出十个包，版本行都是第一次那个时刻**
- 改成 `GenerateBuildId` 任务：执行期取时间，`SOURCE_DATE_EPOCH` 走 `@Input`（环境变量一变自动重跑，
  不再需要手工 `--rerun-tasks`），产物是 `values/build_id.xml`，由
  `variant.sources.res?.addGeneratedSourceDirectory(...)` 挂进各变体
- 可复现口径不变：给了 `SOURCE_DATE_EPOCH` 就用它，不给取当下；时区仍固定 `Asia/Shanghai`（不跟构建机漂）
- **但它故意不参与增量判定**（`outputs.upToDateWhen { false }`）：改成任务之后立刻发现，
  「现在几点」不是任务输入 —— 默认的 UP-TO-DATE 判定会让它停在更早那一次。
  出包验证时实测踩到：改一行注释重新出包，debug 包里还是 **6 分钟前**那个时刻
  （`17:05:51`，而实际打包是 `17:11:30`）。这个值就是给人「对上时间」用的，差几分钟还能解释、
  差几天就误导，所以宁可每次重新生成。代价只是资源重新合并 + 重新打包，R8 不受影响
  （字符串资源不进混淆）。验证方式：连跑两次 `:app:generateBuildIdDebug`，
  得到 `17:13:31` → `17:13:37`，且第二次没有 UP-TO-DATE 标记
- 取值过一道 XML 转义 —— 格式是固定日期串、理论上不含特殊字符，但将来若被人改成带 `&` 的形态，
  不该以「资源编译报错」的方式被发现
- **为什么另起一个 `onVariants { }`**：原来那个在 debug 上会 `return@onVariants` 提前退出（debug 不封存资产），
  两件事适用条件不同，混在一起就得手工排顺序
- `buildFeatures.resValues` 改成显式 `false`（AGP 9 默认就是 false，写出来是为了让人知道「本模块不用它」，
  而不是「忘了开」）

**验证**（不是推的）：

- `./gradlew gate` 首次：`BUILD SUCCESSFUL in 41s` + `Configuration cache entry stored.`
- 再跑一次：`Reusing configuration cache.` + 全部 `UP-TO-DATE`，**3 秒**
- `:app:generateBuildIdDebug` 真的执行了，产物内容为 `2026-10-17 17:05:51`
- 三个变体的 `R.txt` 里都有 `int string build_id 0x0` ⇒ 生成目录确实被当 res 合并了
  （**必须查这个**：代码是按名字 `getIdentifier("build_id", …)` 取的，不是 `R.string.build_id`，
  所以「资源没进包」不会编译失败，只会在运行期退回 `ModuleInfo.BUILD_ID`）
- 三个包实际出完之后，用 `aapt2 dump resources <apk> | grep -A1 string/build_id` 从
  `resources.arsc` 里直接读到了值（debug `17:05:51` / release 与 beta `17:11:30`）——
  这一条同时证了**资源收缩没删掉它**（`res/raw/keep.xml` 那条规则有效）。三档体积与差异判据
  （`tools/check_variants.py`）也复查过，与改之前一致

**没做成的一条**：Defender 排除目录。查下来这台机器的**实时保护本来就是关的**
（`RealTimeProtectionEnabled: False`），没有扫描可排除 —— 我先前那句「Defender 扫 `build/`
要多花 20~40%」对这台机器不成立。另外加排除需要管理员权限，当前会话不是。

### 进程名解析：截到第一个 `\0`，不再只削尾部

- `/proc/<pid>/cmdline` 的格式是**参数逐个用 `\0` 隔开、末尾再补一个 `\0`**。原来的
  `.trimEnd('\u0000').trim()` 只削尾部：进程一旦带 argv（`com.oplus.gesture\0--some-arg\0`），
  留下的就是 `com.oplus.gesture\0--some-arg`，与进程名比对永远不等 —— 表现是
  **「进程明明在，却一个 Hook 都没装」，且不报错**
- 两处同改：`KeyModule.currentProcessName()`（决定装哪套 Hook，判据最重）与
  `PageControl.hostMainPids()`（重启时要杀的主进程 pid，原来按 `==` 精确比对，同样会漏杀）
- 统一成 `.takeWhile { it != '\u0000' }.trim()`：不用 `split('\0').first()`，后者会为整段 argv
  建一个 List，而这里只要前缀。空 cmdline（内核线程）得空串 ⇒ 走 `else ->` 分支，符合预期

### 反射：按字面签名查找时，原始类型与装箱类型互认

- `Reflect.method(cls, name, vararg params)` 原来两段都要求**类型逐个相等**：
  `getDeclaredMethod` 是 `Class` 身份比较（`Integer.class != int.class`），退化的「名字 + 参数个数」
  那一段又完全不看类型。于是传 `Int::class.java`（= `Integer.class`）去查 `f(int)`
  **静默返回 null**，日志上看起来就是「这条 ROM 没有这个方法」
- 中间加一层 `methodBySignature`：按 `methodsOf` 全集挑同名同个数的候选，`signatureScore`
  打三档分（`0` 对不上 / `1` 只差装箱 / `2` 逐个相等），`pickScored` **取最高档，那一档唯一才返回**
- 只认 Java 那八对固定映射，**不做宽化/窄化**：`int` 不匹配 `long` —— 宽化会让 `f(int)` 被
  `f(long)` 顶上，`invoke` 虽然过得去，语义已经变了
- 真重载（`f(int)` 与 `f(Integer)` 同时在）时不猜：同档多个候选就返回 null，退到「按参数个数」那一段
- 判据是**实跑验证**的，不是推的：`/tmp/refltest` 里用一份 Java 类跑了七条用例
  （装箱查原生 / 原生查装箱 / 两组重载 / 精确命中 / 错个数 / 错名字），含一条即时发现并修掉的
  判断错误 —— 早先写成「只要候选不唯一就返回 null」，会把「`int.class` 查 `{f(int)=2分, f(Integer)=1分}`」
  这种本该命中的情形一起判成歧义
- 顺带记下两处**故意不走这层**的地方：`ProbeCall` 用 `getDeclaredMethod` 精确签名
  （`Reflect.method` 的兜底匹配曾把 `Bundle` 形参误配上），`FlexibleAnim` 的 setter 显式传
  `java.lang.Integer.TYPE`。两处都保留原样 —— 它们要的正是「签名不对就失败」

### 测试命令执行器：页面关掉时释放

- `testRunnerCache` 原先是 `ui/screen/command/CommandLibrary.kt` 里的一个裸 `private var`，
  注释写明「本进程只建一份」—— **没有任何释放时点**
- 它持的东西不只 Context：`FlashlightController` 会在第一次 toggle 时往 `CameraManager`
  注册一条 `TorchCallback`，进程里不会自己摘。在 `:ui`（设置页进程）里，这就是
  「试几次手电筒命令、再进出几轮设置页 ⇒ 系统里堆几份没人用的注册」
- 收成 `ui/state/TestRunnerCache`（`acquire` / `release`），由 `SettingsPageHooks.clearPageRefs`
  在关页那一个明确时点调 `release()`；下次进页第一次点「测试」再新建
- 仍是 `internal`：返回类型 `ActionRunner` 是 `internal`，`public` 会报
  「exposes its internal return type」
- 用的还是 `applicationContext`（执行器会把 Context 一直拿着）—— 那是**有界**的一句几 KB，
  比钉住一个已销毁 Activity 及其整棵 View 树轻得多

### 健壮性修复（外部审查清单里核实成立的那几条）

- **手电筒**：由控制中心 / 锁屏磁贴关灯后 `torchOn` 不跟随，下一次按侧键会去「关一个已经关着的灯」——
  表现为按一下没反应、要连按两次。现在认下的那颗摄像头状态是权威，跟着系统回调走
- **命令链的步骤间隔**：连续的 shell 步骤原本无条件合并成 `a; b`（零延迟），
  用户配的「步骤间延时」被抹掉；现在有间隔就逐步单独派发，间隔由原有的延时续步撑住
- **配置被编辑器改坏后读不懂**：解混淆前滤掉空白与 `\u00A0`／BOM，
  避免「记事本另存一次 ⇒ 配置判读不懂 ⇒ 界面怎么改都保存失败」
- **Messenger 服务绑不上时白等 3 秒**：`bindService` 同步返回 false 就立刻报失败，不再等超时
- **设置页关页后引用不释放**：补上宿主 Activity 的 `onDestroy` Hook，
  顶栏返回 / 系统回收 / 手势退出都会清掉页面与宿主视图树的静态引用
- **原子写盘失败残留 `.tmp`**：写入阶段抛异常时把半截临时文件删掉
- **APK zip 兜底路径恒失败**：`assets/` 前缀缺失，按 zip 直读资产永远返回 null（只影响兜底那条路）
- **未来时间戳锁死手势**：`sentAt` 落在未来时按过期处理，避免一次脏数据把该手势永久吞掉
- **长按连发时多余的补发广播**：连发阶段不再排 300ms 后的补发，松手后不积压废消息
- **SurfaceControl 事务**：反射调用抛异常时补上 `close()`（这条出口原来漏了）
- **shell 管道**：收尾时强关 stdout/stderr，避免脚本派生的常驻子进程占着读线程与 FD

### 建页读盘挪出主线程

- 进设置页那一次要读三份文件（主配置 / 命令库 / 界面偏好），原来全在
  `SettingsPage.createView()` 里**同步**做 —— 而它跑在宿主 Activity 的主线程上（`onCreate` 那条路），
  一次进页就是三趟 `open + readText + parseJSON`：StrictMode 的 diskRead 违规，
  也是「从设置进模块页面偶尔顿一下」的一个来源
- 现在整段读归 `ui/state/PageLoadSnapshot.kt`（纯数据、不碰 Compose 状态），
  由组合期的 `loadPageState()` 放到 `Dispatchers.IO` 上跑，回到主线程只做「把结果写进状态」；
  建页时那次主动同步给注入侧的配置广播也一并挪了过去（它内部要读命令库算指纹）

  画出「模块未开、全无操作」的界面、几十毫秒后再翻成真值，用户看到的是开关自己弹一下
- 三态纪律原样保留（`Ok` / `Absent` 可写回、`Unreadable` 进只读），且读盘函数**不抛**：
  真出意外就退回「两份都只读」，页面照常能看但一个字节都写不回去 —— 不会停在底色上
